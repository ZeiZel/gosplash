# Фаза 0 — фундамент и переезд

Самая скучная фаза и единственная, после которой структура репозитория больше
не меняется. Новых возможностей у пользователя не прибавилось: `make demo`
делает ровно то же, что делал раньше. Прибавилось другое — теперь видно, что
именно происходит внутри.

## Что сделано

### 2. Переезд структуры

| Было | Стало |
|---|---|
| модули `gosplash/libs` + `gosplash/configs` | корневой модуль `gosplash` |
| `libs/pkg/db`, `s3`, `kafka`, `req`+`res` | `pkg/dbx`, `pkg/s3x`, `pkg/kafkax`, `pkg/httpx` |
| `configs/` | `pkg/config` |
| `libs/pkg/api` | `gen/go` |
| `proto/<домен>/v1`, пакет `media.v1` | `proto/gosplash/<домен>/v1`, пакет `gosplash.media.v1` |
| `buf.yaml` в корне | `proto/buf.yaml` |
| `docker/*.yml` + корневой compose | `deploy/compose/` |
| `services/*/cmd/main.go` | `services/*/cmd/<сервис>/main.go` |

Удалён `libs/pkg/event` — внутрипроцессная шина событий. Она не использовалась
ни одной строчкой и противоречила правилу «как только событие нужно кому-то за
пределами процесса, это Kafka».

media и catalog переведены на **ports & adapters**:

```
internal/domain/    предметная область, без тегов gorm/json/protobuf
internal/ports/     интерфейсы, объявленные рядом с тем, кто ими пользуется
internal/app/       сценарии: тестируются без базы, S3 и Kafka
internal/adapters/  pg, kafka, grpc, http
```

Доменная модель и строка таблицы — **разные типы** с ручным отображением между
ними. Это две функции лишнего кода на сущность; взамен изменение схемы таблицы
больше не правит предметную область, а `internal/app/service_test.go`
прогоняет весь сценарий загрузки за 200 мс без единого контейнера.

### 3. Именование и контракты

- `Image` → `Photo`, таблица `images` → `photos`, `catalog_images` →
  `listings`, ручки `/media/images` → `/media/photos`,
  `/catalog/images` → `/catalog/listings`.
- Топики по конвенции `<домен>.<сущность>.<факт>`: `media.photo.uploaded`,
  `media.photo.thumbnail-ready`, `catalog.listing.published`,
  `order.order.placed`, `wallet.account.debited`, `analytics.photo.viewed`,
  плюс `.retry` и `.dlq` к основным. Имена собраны в `pkg/kafkax/topics.go`.
- Введён `gosplash.events.v1.Envelope`: `event_id` (uuid v7), `event_type`,
  `aggregate_id`, `occurred_at_unix_ms`, `schema_version`, `Any payload`.
  В топик пишется только он.
- Заголовки Kafka: `event_id`, `event_type`, `producer`, `traceparent`.

### 4. Наблюдаемость

`pkg/otelx` — один вызов `Setup` из `main` поднимает всё:

- трейсы OTLP → коллектор → Tempo, сэмплер `ParentBased`;
- метрики через Prometheus-экспортёр OTel, отдаются на `/metrics`;
- `slog` в JSON, в каждой строке `trace_id` и `span_id` — именно это
  склеивает логи с трейсами;
- `otel.SetTextMapPropagator` с W3C TraceContext.

Инструментировано: HTTP (`otelhttp` + собственные RED-метрики), gRPC
(`otelgrpc` на сервере и клиенте), GORM (`gorm.io/plugin/opentelemetry`),
Kafka (`pkg/kafkax/trace.go` — `traceparent` в заголовках записи).

`pkg/httpx` — recovery, логирование, RED-метрики, `/healthz`, `/readyz`,
graceful shutdown, служебный сервер с `/metrics` и `/debug/pprof` на отдельном
порту.

`deploy/compose/docker-compose.observability.yml` + `deploy/observability/` — коллектор,
Tempo, Prometheus (с правилами алертов из §9), Loki, promtail, Grafana с
дашбордом «gosplash overview» и настроенными переходами между тремя сигналами.

### 5. Тесты

Раньше их не было ни одного. Сейчас 42 теста (64 вместе с подтестами) в шести пакетах:

| Пакет | Что проверяется |
|---|---|
| `pkg/dbx` | детерминированность и равномерность `ShardIndex`; зафиксирована известная слабость `hash % N` при добавлении шарда |
| `pkg/kafkax` | конверт туда-обратно, уникальность и монотонность `event_id`, отказ при чужом типе payload |
| `pkg/kafkax` | **trace-контекст переживает Kafka** — без этого теста разрыв трейса на границе топика заметить почти невозможно |
| `pkg/httpx` | liveness отвечает 200 при упавшей базе, readiness — 503; общий бюджет времени на проверки |
| `pkg/config` | разбор переменных, остановка `shardDSNs` на первой дыре в нумерации |
| `services/media/internal/app` | порядок шагов загрузки и что происходит при падении каждого |
| `services/catalog/internal/app` | идемпотентность индексатора, разница между временной и постоянной ошибкой |

Два теста написаны так, чтобы **упасть, когда придёт время**: тест «событие
потеряно, но загрузка успешна» должен сломаться при появлении outbox в фазе 1,
а тест про переезд ключей при `2 → 3` шарда — при переходе на consistent
hashing. Падение такого теста — не поломка, а напоминание обновить ADR.

## Как проверить

```bash
make up           # включая стек наблюдаемости
make doctor       # каждый компонент отвечает OK
make migrate      # схемы всех баз + репликация каталога
make run-all      # media и catalog, в отдельном терминале
make demo-0       # готовность, метрики, targets Prometheus
make demo         # прежний сквозной сценарий загрузки
make test         # 42 теста, зелено
```

Что смотреть глазами:

1. **Трейс целиком.** Grafana → Explore → Tempo, поиск по `service.name=media`.
   В одном трейсе: HTTP-запрос → `SELECT`/`INSERT` в PostgreSQL →
   `media.photo.uploaded publish` → `media.photo.uploaded process` в catalog →
   gRPC `GetPhoto` обратно в media. Если бы `traceparent` не клался в
   заголовки сообщения, вместо одного трейса было бы три.
2. **Переход трейс → логи.** Открыть спан, нажать «Logs for this span».
   Работает потому, что `pkg/otelx` кладёт `trace_id` в каждую строку `slog`.
3. **Readiness против liveness.** `docker compose stop kafka`, затем
   `curl localhost:58080/media/readyz` — 503 с причиной прямо в теле ответа,
   а `/media/healthz` остаётся 200. Разница в том, что первое убирает под из
   балансировки, а второе вызвало бы его перезапуск.
4. **Метрики.** `make metrics P=8201`, `make targets`, `make alerts`.

## Чего сознательно не сделано

- **Топики созданы, но `.retry` и `.dlq` никто не читает.** Классификация
  ошибок, задержанный retry и переливка из DLQ — фаза 1.
- **Публикация события идёт после коммита.** Упадёт Kafka — фото сохранится,
  а в каталог не попадёт. Это зафиксировано тестом и лечится outbox в фазе 1.
- **`processed_events` нет.** Идемпотентность каталога держится только на том,
  что upsert безопасно повторить. Для «записать состояние» этого хватает, для
  «сделать превью» — уже нет.
- **Метрика `kafka_consumer_lag` объявлена в дашборде и алертах, но никто её
  не пишет.** Сбор через `kadm` — фаза 1; панель и правило оставлены заранее,
  чтобы было видно, чего не хватает.
- **Redis поднят, но не используется ни одной строчкой Go.** Фаза 2.
- **Аутентификации нет**, пользователь по-прежнему берётся из `X-User-Id`.
  JWT-интерсептор — фаза 3.
- **CI не настроен.** `golangci-lint`, `buf breaking`, `go test -race`
  и проверка «нет прямого Produce» — фаза 1, вместе с первым кодом, который
  эту проверку может нарушить.

## Проверено и не проверено

Собирается, `go vet` чист, `buf lint` чист, все тесты зелёные, `docker compose
config` валиден и пути к конфигам резолвятся.

**Не проверено запуском:** на машине, где делалась фаза, не был запущен
docker-демон, поэтому стек не поднимался и `make demo-0` не прогонялся живьём.
Первое, что стоит сделать, — `make nuke && make up && make doctor`: полное
удаление томов здесь обязательно, потому что переименование задело имена баз,
бакетов и топиков, и старые тома содержат несовместимые данные.
