# ADR 0018. Идемпотентность HTTP: Redis против таблицы в PostgreSQL

- **Статус:** принято, 2026-09-12
- **Фаза:** 3

## Контекст

`POST /orders` принимает заголовок `Idempotency-Key`. Без него один клик
«купить» превращается в несколько заказов при любом клиентском ретрае —
мобильный клиент переотправил запрос после таймаута, пользователь нажал
кнопку дважды. Нужен способ сказать «этот ключ уже обрабатывается» или
«этот ключ уже обработан, вот готовый ответ», причём под нагрузкой и без
гонок между параллельными повторами.

`pkg/redisx.Client.Begin/Complete` (фаза 2) уже даёт для этого готовый
примитив: `SET NX EX ttl` — атомарная попытка занять ключ, три исхода
(`IdempotencyFree` / `IdempotencyInProgress` / `IdempotencyDone`). Вопрос
фазы 3 — достаточно ли этого одного примитива для order, или нужен ещё
и `idempotency_keys` в PostgreSQL, и если нужен — то как они соотносятся.

## Решение

Redis остаётся быстрым путём, но не единственным хранилищем. PostgreSQL
(таблица `idempotency_keys`) — источник правды. Полная реализация —
`internal/adapters/idempotency/store.go`.

Три исхода `Begin`, если смотреть на реализацию, а не на интерфейс
(`ports.IdempotencyStore`, тот же список из трёх, что и в `pkg/redisx`):

1. Redis отвечает `IdempotencyInProgress` или `IdempotencyDone` — ответ
   берётся ИЗ Redis, в PostgreSQL не ходим вовсе. Это горячий путь: почти
   все повторы приходят, пока ключ ещё свежий в кэше.
2. Redis недоступен целиком (ошибка транспорта, а не логический ответ) —
   работаем напрямую с PostgreSQL: `INSERT ... ON CONFLICT DO NOTHING`,
   тот же трюк «атомарно проверить и занять», что и `SET NX` в Redis.
3. Redis отвечает `IdempotencyFree` — САМЫЙ ВАЖНЫЙ случай. «Свободно» — это
   ЕДИНСТВЕННЫЙ исход, который Redis может выдать ОШИБОЧНО: если ключ был
   вытеснен по памяти или Redis перезапустился без persistence
   (`deploy/compose/redis.yml` её не настраивает — простота локальной
   разработки важнее), Redis искренне не помнит, что ключ уже был занят.
   `IdempotencyInProgress`/`IdempotencyDone` он не подделает: раз ключ
   найден, содержимое достоверно. А вот отсутствие ключа ничего не
   доказывает. Поэтому «свободно» от Redis всегда перепроверяется
   в PostgreSQL, прежде чем разрешить операцию.

`Complete` пишет сначала в PostgreSQL (источник правды, безусловно), потом
пытается обновить Redis (кэш на будущее; неудача здесь не проваливает уже
завершённую операцию, только следующий повтор запроса будет отвечать чуть
медленнее — придёт через PostgreSQL).

### Почему не одна связка целиком

- **Только Redis.** Дешёво и достаточно для сервисов, где повторная
  обработка неприятна, но не катастрофична (например, кэш каталога). Для
  «списать деньги за заказ» потерянный ключ означает двойное списание —
  цена ошибки слишком высока для хранилища без гарантии сохранности.
- **Только PostgreSQL.** Надёжно, но каждая проверка идемпотентности — это
  запрос к primary. `POST /orders` — путь, где повторов МНОГО (ровно
  потому, что клиенты ретраят сетевые сбои), и все они бы шли мимо кэша
  прямо в ту же базу, которая уже занята записью самих заказов.

## Последствия

**Хорошее.** Обычный (успешный, без потерь Redis) путь остаётся быстрым:
одна команда Redis. Потеря ключа в Redis не превращается в двойное
списание — PostgreSQL перепроверяет ровно тот единственный случай, когда
это нужно.

**Плохое.**

- Два хранилища вместо одного — лишний код (`internal/adapters/idempotency`),
  лишняя таблица, лишняя миграция.
- `beginPG` — на пути, где Redis соврал про «свободно», добавляется поход
  в PostgreSQL, то есть именно на потенциально самом нагруженном пути
  (первый запрос с новым ключом) есть небольшой шанс лишней задержки —
  но не больше одной, если Redis сам по себе доступен.
- Гонка между Redis и PostgreSQL всё ещё возможна В ПРИНЦИПЕ на уровне
  «Complete записал в PostgreSQL, но упал до записи в Redis» — следующий
  повтор в этом крошечном окне пойдёт через `beginPG` вместо кэша.
  Корректность не страдает (PostgreSQL как раз для этого и существует),
  страдает только задержка одного конкретного повтора.

**Известное ограничение, не решённое в этой фазе.** Если процесс упал
между `Begin` (ключ помечен `in_progress`) и `Complete`, ключ остаётся
`in_progress` НАВСЕГДА в PostgreSQL (Redis-копия сама протухнет по TTL,
но авторитетная запись в PostgreSQL — нет). Повторный запрос с тем же
`Idempotency-Key` будет получать 409 бесконечно, а не «попробовать снова».
В проде это лечится фоновым разгребателем зависших `in_progress` строк
старше своего TTL; здесь его нет — заказ, застрявший так, виден в таблице
`idempotency_keys` и разбирается вручную. Явный, а не молчаливый пробел.
