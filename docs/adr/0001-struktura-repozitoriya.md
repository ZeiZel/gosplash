# ADR 0001. Структура репозитория: миграция на раскладку спецификации

- **Статус:** принято, 2026-09-12
- **Фаза:** 0

## Контекст

Репозиторий начинался как учебный проект «photostock» и сложился в такую
раскладку:

```
libs/                 модуль gosplash/libs: pkg/{db,kafka,s3,req,res,event} + pkg/api
configs/              модуль gosplash/configs: чтение переменных окружения
proto/<domain>/v1/    контракты, пакет protobuf без namespace: media.v1
docker/*.yml          стеки compose, подключаются через include из корня
buf.yaml, buf.gen.yaml в корне, генерация в libs/pkg/api
```

Спецификация проекта (§1) задаёт другую:

```
pkg/<name>/                      общие библиотеки в корне
proto/gosplash/<domain>/v1/      контракты с namespace: gosplash.media.v1
gen/go/                          сгенерированный код
deploy/compose/                  стеки compose
```

Правило §0.1 запрещает переписывать работающее без причины, и обе раскладки
рабочие. Значит, вопрос не «какая правильнее», а «стоит ли переезд того, что он
стоит».

Аргументы против переезда: половина дня механической правки импортов до первой
новой строчки кода; риск сломать `make demo`, который сейчас проходит.

Аргументы за: спецификация ссылается на пути из своей раскладки в каждом
параграфе (§3.3 «`pkg/kafkax`», §4.1 «`pkg/outbox`», §5 «`pkg/redisx`», §9
«`pkg/otelx`»). Держать «переводчик» между текстом спецификации и деревом
файлов придётся все семь фаз — это постоянный налог, а переезд разовый. Проект
учебный, и человек, читающий его вместе со спецификацией, не должен каждый раз
соображать, что `pkg/kafkax` из текста — это `libs/pkg/kafkax` в дереве.

Отдельный аргумент за namespace в protobuf-пакетах: сейчас пакет называется
`media.v1`. Это глобальное имя в реестре типов protobuf, и оно занимает слово
`media` для всех, кто когда-либо слинкует наш код со своим. `gosplash.media.v1`
такой проблемы не создаёт. То же касается `google.protobuf.Any` в `Envelope`:
`Any` хранит **полное** имя типа, и без namespace конфликт становится вопросом
времени.

## Решение

Мигрировать на раскладку спецификации целиком, в фазе 0, одним заходом.

Конкретно:

| Было | Стало |
|---|---|
| модуль `gosplash/libs` + `gosplash/configs` | корневой модуль `gosplash` |
| `libs/pkg/db` | `pkg/dbx` |
| `libs/pkg/s3` | `pkg/s3x` |
| `libs/pkg/kafka` | `pkg/kafkax` (переписывается в фазе 1) |
| `libs/pkg/{req,res}` | `pkg/httpx` |
| `libs/pkg/event` | удаляется: внутрипроцессная шина не нужна, всё через Kafka |
| `configs/` | `pkg/config` |
| `libs/pkg/api` | `gen/go` |
| `proto/<d>/v1` | `proto/gosplash/<d>/v1`, пакет `gosplash.<d>.v1` |
| `docker/*.yml`, `docker-compose.yml` | `deploy/compose/` |
| `buf.yaml`, `buf.gen.yaml` в корне | `proto/buf.yaml`, `proto/buf.gen.yaml` |

Сервисы остаются отдельными Go-модулями — это решение не пересматривается:
в проде в образ попадает один сервис, и отдельный `go.mod` не даёт случайно
импортировать соседа.

Переезд выполняется вместе с переименованием сущностей ([ADR 0003](0003-imenovanie-sobytiy-i-envelope.md))
и переводом media/catalog на hexagonal-раскладку `internal/{domain,app,adapters,ports}`:
три механических изменения в одном коммите дешевле трёх подряд, потому что
каждое из них всё равно трогает те же файлы.

## Последствия

**Хорошее.** Пути из спецификации совпадают с путями в дереве. Один корневой
модуль вместо двух — меньше `go.mod` для синхронизации при обновлении
зависимостей. Protobuf-пакеты получают namespace.

**Плохое — и с этим придётся жить.** Импорт сгенерированного кода становится
длинным и с удвоением:

```go
mediav1 "gosplash/gen/go/gosplash/media/v1"
```

Левое `gosplash` — путь Go-модуля, правое — namespace protobuf-пакета
(`gosplash.media.v1`), и `paths=source_relative` честно раскладывает файлы по
пути пакета. Избавиться можно было бы, отказавшись от namespace в protobuf, но
это ровно та проблема, ради которой namespace и вводится. Смягчается алиасом
импорта — он и так используется везде.

**Разовая цена.** Правятся все импорты, `go.work`, `buf.gen.yaml`
(`go_package_prefix: gosplash/gen/go`), `Makefile` (пути к compose-файлам и
целям генерации), `.env.example`, `README.md`. Проверка: `make demo` даёт тот же
результат, что до переезда.

**Что осталось за скобками.** `tools/automigrate` и `tools/mediactl` сохраняют
собственные `go.mod` — они не часть библиотеки и их зависимости не должны
протекать в корневой модуль.
