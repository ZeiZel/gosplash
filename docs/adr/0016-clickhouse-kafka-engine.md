# 0016. ClickHouse через Kafka engine против push из Go

Фаза: 4. Статус: принято.

## Контекст

analytics-сервису нужно попасть из Kafka в ClickHouse: `analytics.photo.viewed`
(из catalog, событие `PhotoViewed`) и `order.order.paid` (из order, событие
`OrderPaid`). Спецификация фазы прямо просит рассмотреть **Kafka engine** —
встроенный в ClickHouse способ читать топик Kafka самим движком, без
отдельного приложения-консьюмера: таблица с `ENGINE = Kafka(...)` подписывается
на топик, а материализованное представление перекладывает прочитанное в
обычную MergeTree-таблицу. Кода на Go при этом не нужно вообще — вся цепочка
живёт в SQL.

Ровно это и стоило проверить в первую очередь, вместо того чтобы взять более
привычный вариант (консьюмер на Go) по умолчанию.

### Почему Kafka engine здесь не работает

В топики проекта **всегда** пишется не сырой payload, а конверт `Envelope`
(`proto/gosplash/events/v1/events.proto`):

```protobuf
message Envelope {
  string event_id = 1;
  string event_type = 2;
  string aggregate_id = 3;
  int64 occurred_at_unix_ms = 4;
  int32 schema_version = 5;
  google.protobuf.Any payload = 6;   // ← вот тут проблема
}
```

`Envelope.payload` — это `google.protobuf.Any`: обёртка с полем `type_url`
(строка вида `"type.googleapis.com/gosplash.events.v1.PhotoViewed"`) и байтами
сериализованного сообщения ВНУТРИ него. Kafka engine с `kafka_format =
'Protobuf'` (или `'ProtobufSingle'`) умеет разобрать **один плоский,** заранее
известный протобаф-тип по `.proto`-схеме, которую ему явно указывают
(`format_schema = 'events.proto:PhotoViewed'`). Он не умеет и не обязан уметь:

- заглянуть внутрь `Any` и по `type_url` понять, какую схему применить к
  вложенным байтам — `Any` для движка ClickHouse просто ДВА произвольных поля
  (`string type_url`, `bytes value`), а не «путь к другому сообщению»;
- «размотать» вложенный `Any` даже если бы знал схему: `Protobuf`-формат
  ClickHouse ожидает byte-стрим, который является ЦЕЛЫМ сообщением заявленного
  типа, а не сообщением-контейнером, у которого одно из полей — это ЕЩЁ ОДНО
  сериализованное сообщение другого типа.

Проверено не по документации, а руками: `kafka_format='ProtobufSingle'` с
`format_schema` на `Envelope` действительно читает `event_id`, `event_type`,
`aggregate_id` — но `payload` в таблице оказывается парой
`(type_url String, value String)`, где `value` — это НЕПРОЗРАЧНЫЕ байты
`PhotoViewed`, а не его поля. Прочитать `photo_id`/`author_id`/`viewer_id` из
этого `value` штатными средствами SQL (`Protobuf`/`JSON` парсинг колонки)
ClickHouse не может — это произвольные бинарные байты произвольного
протобаф-сообщения, а не строка формата, который движок понимает.

### Единственный обходной путь — и почему он отклонён

Обойти это можно было бы, только если бы **продюсер** писал в топик голый
`PhotoViewed`/`OrderPaid` без конверта — тогда `kafka_format='ProtobufSingle'`
+ `format_schema` сработали бы штатно. Но:

- продюсер — `services/catalog` (просмотры) и `services/order` (покупки),
  оба вне зоны ответственности этой фазы, их код менять нельзя;
- даже будь это разрешено, отказ от `Envelope` для одного конкретного топика
  сломал бы инварианты, ради которых конверт вообще существует
  (дедупликация по `event_id` без разбора payload, DLQ по битым сообщениям,
  `schema_version` — все три расписаны в шапке `events.proto`), и сделал бы
  один топик проекта устроенным принципиально иначе, чем все остальные —
  ради удобства ОДНОГО потребителя.

Значит, Kafka engine в его прямом виде не сработал бы, даже потратив на него
всю фазу.

## Решение

**Консьюмер на Go** (`internal/adapters/kafka`), читающий оба топика через
`pkg/kafkax.Consumer` (тот же пакет, что и в `catalog`/`thumbnail-worker`),
разбирающий `Envelope` через `kafkax.UnmarshalPayload[T]` (`anypb.UnmarshalTo`
внутри) и пишущий строки в ClickHouse **батчами** через `clickhouse-go/v2`
(`internal/adapters/clickhouse`), а не по одной.

Kafka engine остаётся тем, чем и должен быть в этом документе, — рассмотренной
и отклонённой альтернативой, а не работающим, но неиспользованным вариантом:
показанное выше — не гипотеза, а воспроизведённое на живом ClickHouse 25.8
поведение.

### Батчинг: batch-before-commit, а не async-буфер

Внутри консьюмера строки не вставляются по одной (см. README сервиса, раздел
«почему построчная вставка — антипаттерн»: каждый `INSERT` — это новый парт на
диске, а фоновые мержи не успевают за темпом просмотров). Накопление и
батч-вставка сделаны в `internal/adapters/clickhouse/batch.go`
(`Writer[T]`) с ключевым свойством: `Add()` **блокирует** вызывающего (то
есть `kafkax.Consumer`, обрабатывающий очередное сообщение партиции) до тех
пор, пока пачка, в которую попала эта строка, не будет **успешно** отправлена
в ClickHouse.

Это сознательно ИНАЧЕ, чем `services/catalog/internal/adapters/kafka/
view_batcher.go` (тот же PhotoViewed, но на стороне ПРОДЮСЕРА в Kafka):
`ViewBatcher.Enqueue` никогда не блокирует и никогда не возвращает ошибку —
там буфер живёт МЕЖДУ прикладным кодом и Kafka, и его потеря при падении
процесса означает, что событие никогда не попадало в Kafka вовсе (источника
для повтора нет, но и НИЧЕГО не закоммичено). Здесь буфер живёт МЕЖДУ Kafka
и ClickHouse — на ПОСЛЕДНЕМ шаге. Верни `Add()` `nil` сразу после постановки
в буфер, `kafkax.Consumer` закоммитил бы offset Kafka ДО фактической вставки
строки в ClickHouse; упади процесс между этими двумя моментами — offset уже
продвинут, Kafka никогда не пришлёт сообщение снова, а строка исчезла из
отчёта без всякого способа это заметить или исправить.

## Последствия

**Хорошо:**

- Envelope-инвариант (дедупликация, DLQ, версионирование схемы) не
  нарушается ни для одного топика проекта — консьюмер разбирает его тем же
  способом, что и все остальные сервисы (`kafkax.UnmarshalPayload`).
- Ошибка обработки одного сообщения классифицируется retryable/permanent тем
  же механизмом, что и везде (`pkg/kafkax/errors.go`) — например, конверт с
  чужим `event_type` в топике уходит прямиком в DLQ, не тратя окно ретраев.
- batch-before-commit устраняет самый неприятный класс потерь для
  аналитической витрины — молчаливую дыру в отчёте, которую нечем закрыть.

**Чем платим:**

- Лишний прыжок кода между Kafka и ClickHouse: Kafka engine избавил бы от
  этого пакета целиком (SQL сам читает топик). Мы платим кодом
  `internal/adapters/kafka` + `internal/adapters/clickhouse/batch.go` за то,
  чтобы вообще суметь разобрать `Envelope`.
- Второй процесс между Kafka и ClickHouse — точка отказа и объект
  эксплуатации (метрики лага, память под буфер, отдельный деплой), которой
  не было бы при Kafka engine — там ClickHouse читает топик сам, никакого
  внешнего процесса нет вовсе.
- batch-before-commit — это НЕ «ровно один раз». При падении процесса МЕЖДУ
  успешной вставкой пачки и тем, как `Add()` успевает сообщить об этом всем
  ожидающим строкам, часть сообщений придёт из Kafka повторно после
  перезапуска (их offset ещё не закоммичен) и будет вставлена ЕЩЁ РАЗ.
  ClickHouse не проверяет уникальность (см. README, раздел про разреженный
  индекс) — получится ДУБЛИКАТ строки, а не ошибка вставки. Это
  воспроизведено намеренно: `internal/adapters/clickhouse/integration_test.go
  :TestWriter_DublirovaniePriPovtorePosleUpavshegoOffseta` фиксирует именно
  такое поведение, а не борется с ним. Компромисс осознанный: между «иногда
  дважды» (дубликат — видимая, чинимая задним числом проблема:
  `ReplacingMergeTree`, дедупликация в запросе) и «иногда никогда» (дыра в
  отчёте — невидимая и нечинимая, потому что источника события в Kafka
  больше нет) выбрано первое.
- Для `photo_views` (объём на порядки больше, чем у `purchases`) это ещё и
  симметрично тому же выбору, который `services/catalog` уже сделал на
  стороне продюсера для этого же события (`view_batcher.go`): аналитика
  просмотров и так уже приблизительна по спецификации
  (`unique_viewers_approx` в `analytics.proto`), и лишняя строка на
  редчайший рестарт процесса не меняет ни одного решения, принимаемого по
  этой метрике.
- Если объём событий вырастет настолько, что процесс консьюмера перестанет
  успевать (а не ClickHouse — вставка батчами уже снимает узкое место со
  стороны БД), придётся либо горизонтально масштабировать консьюмер
  (партиции топика это позволяют — `pkg/kafkax` уже даёт горутину на
  партицию), либо тогда пересмотреть Kafka engine ещё раз — но уже вместе
  с изменением контракта продюсера, что выходит за рамки одной фазы.
