# ADR 0002. Шардирование media сохраняется вопреки §13 спецификации

- **Статус:** принято, 2026-09-12
- **Фаза:** 0

## Контекст

Спецификация говорит о базах данных две вещи:

- §2: «у каждого сервиса своя схема PgSQL (`media`, `catalog`, `wallet`,
  `order`). Кросс-сервисных JOIN нет»;
- §13 (non-goals): «не шардировать PgSQL в этих фазах».

В репозитории `media` уже шардирован и работает: `pkg/dbx.Shards` считает
`fnv32(user_id) % N`, репозиторий выбирает соединение по ключу, запросы без
ключа шардирования идут scatter-gather'ом по всем базам, `tools/automigrate`
накатывает схему на каждый шард, в compose подняты `pg-shard-0` и `pg-shard-1`.

Шардирование здесь не деталь реализации, а сквозная учебная тема, протёкшая
в контракты:

- `media.v1.GetImageRequest` содержит обязательный `user_id` — без ключа
  шардирования сервис не знает, на какой базе искать строку. Это самое
  наглядное в проекте доказательство тезиса «шардирование меняет API»;
- `ImageUploaded` несёт `user_id` по той же причине;
- существование самого `catalog` мотивировано тем, что публичную ленту нельзя
  строить scatter-gather'ом по шардам;
- модель `Image` не использует `gorm.Model`, потому что автоинкремент в
  шардированной таблице выдаёт коллизии между шардами.

Убрать шардирование — значит выбросить работающий материал, обесценить половину
комментариев в `pkg/dbx` и `services/media`, упростить `media.proto` до вида, в
котором он перестаёт что-либо объяснять, и закрыть этап 5 `TODO.md` (решардинг,
consistent hashing) как неактуальный.

## Решение

Шардирование `media` сохраняется. §13 трактуется как «не добавлять **новое**
шардирование», а не «удалить существующее»: смысл non-goal — не расширять
объём работ, а удаление работающего кода объём как раз увеличивает.

Новые сервисы (`wallet`, `order`, `analytics`, `search`) шардированными **не
делаются** — у них одна база на сервис, как требует §2. Партиционирование
`ledger_entries` по месяцу остаётся разрешённым (§13 прямо это допускает).

## Последствия

**Главное последствие — цена, которую платят все последующие фазы.** Служебные
таблицы паттернов в media живут **на каждом шарде**, а не в одной базе:

- `outbox` — по копии на шард. Relay обходит все шарды; `outbox_pending` — это
  сумма по шардам, а метрика должна иметь label `shard`, иначе непонятно, где
  затык. Транзакция «метаданные + событие» остаётся однобазовой, потому что обе
  строки ложатся на один и тот же шард (ключ один — `user_id`), — и это,
  собственно, единственная причина, по которой outbox в шардированном сервисе
  вообще возможен;
- `processed_events` в media — так же по шардам;
- запрос «покажи все необработанные события» становится scatter-gather'ом.

Это не осложнение ради осложнения: ровно так выглядит жизнь с шардами в
реальности, и именно этот урок в проекте и нужен. В комментариях к коду
`outbox`-relay пишется явно, почему цикл идёт по `shards.All()`.

**Второе последствие.** В спецификации сервис `media` владеет агрегатом `Photo`
и таблицами `photos`, `outbox` (§2). У нас это `photos` + `outbox` ×N шардов.
Таблица из §2 остаётся верной с точностью до этой оговорки.

**Третье.** `wallet` и `order` находятся в противоположной ситуации: у них по
одной базе, и их outbox-relay выглядит просто. Разница между двумя реализациями
одного паттерна — сама по себе учебный материал, и её стоит проговорить в
`docs/phases/01.md`.

**Риск.** Соблазн «раз уж есть шарды, давайте шардировать и wallet». Не делаем:
деньги в шардированной базе означают невозможность транзакции между счетами, и
это отдельный проект.
