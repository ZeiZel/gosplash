# ADR 0012. Redis-лок против PostgreSQL advisory lock

- **Статус:** принято, 2026-09-12
- **Фаза:** 2

## Контекст

thumbnail-worker обрабатывает `media.photo.uploaded`: скачивает оригинал,
генерирует превью трёх размеров, кладёт их в S3, обновляет запись в media.
Kafka-консьюмер в проекте — это `at-least-once`-доставка (см. ADR 0010): при
ребалансе группы, ретрае после падения пода или дублирующем продюсере одно
и то же сообщение может прийти дважды. Генерация превью — не бесплатная
операция (декодирование, ресайз, кодирование трёх файлов), и делать её
дважды параллельно для одного и того же фото — чистая трата CPU и, в худшем
случае, гонка при записи в S3 одного и того же ключа.

Нужен способ сказать «эту фотографию сейчас кто-то уже обрабатывает,
остальные пусть подождут или отступят». В PostgreSQL для этого есть
advisory lock (`pg_advisory_lock`/`pg_try_advisory_lock`), и в проекте уже
есть подключение к PostgreSQL (media — шардированная база); в фазе 2
появляется Redis. Вопрос — на чём строить именно этот лок.

## Решение

Лок для thumbnail-worker строится на Redis: `SET key token NX PX ttl` для
захвата, Lua-скрипт со сверкой токена для освобождения, watchdog-горутина,
продлевающая TTL, пока обработка идёт. Реализация — `pkg/redisx` (`lock.go`).

### Почему не PostgreSQL advisory lock

Advisory lock в PostgreSQL — это лок, **привязанный к сессии** (или к
транзакции для `pg_advisory_xact_lock`). У этой привязки есть ровно то
свойство, которое здесь мешает: лок автоматически снимается, когда сессия
обрывается — обрыв сети, падение пода, `OOMKilled`. На первый взгляд это
плюс («забыть снять лок невозможно»), но для thumbnail-worker это означает,
что лок живёт **ровно столько, сколько живёт TCP-соединение к Postgres**, а
не столько, сколько нужно для конкретной обработки: если воркер тримит долгую
генерацию превью, а его pod убивают по любой причине, лок пропадает мгновенно
и без всякого TTL — то есть нет предсказуемого окна, в течение которого
конкурент точно не перехватит работу. У Redis-лока с `PX` это окно есть
всегда, явно и настраиваемо, независимо от того, как именно оборвался процесс.

Второй довод — инфраструктурный, а не концептуальный: advisory lock держит
занятым соединение из пула `pkg/dbx` (`SetMaxOpenConns(20)`) на всё время
работы, потому что лок жив, пока жива сессия. Redis не участвует в пуле
соединений к Postgres вообще — лок и основная нагрузка на базу (запись
метаданных превью) не конкурируют за один и тот же дефицитный ресурс.

Третий — Redis уже есть в фазе 2 для cache-aside, rate limiting и
idempotency-key; заводить advisory lock как единственного потребителя
отдельного механизма ради одного сценария менее оправдано, чем один
согласованный API (`pkg/redisx`) для всех паттернов, использующих Redis.

### Почему это не гарантия, а оптимизация — и это принципиально

Ни Redis-лок, ни advisory lock не дают взаимного исключения в строгом
смысле при определённых сбоях. Для Redis-лока (см. подробный разбор в
doc-комментарии `Lock` в `pkg/redisx/lock.go`) это:

- **Сетевое разделение.** Воркер A держит лок, у него рвётся связь с Redis.
  TTL истекает, Redis отдаёт лок воркеру B. B начинает работу. Сеть у A
  восстанавливается — A, ничего не подозревая, продолжает СВОЮ работу. Два
  воркера активны одновременно.
- **Пауза GC (или планировщика ОС) дольше TTL.** Процесс замирает на
  STW-паузе, лок истекает и перехватывается, процесс просыпается и
  продолжает как ни в чём не бывало — с его точки зрения времени не прошло.

Watchdog снижает вероятность false expiry (лок продлевается, пока работа
реально идёт), а сверка токена в Unlock защищает от того, чтобы A не снял
уже ЧУЖОЙ (принадлежащий B) лок при завершении своей работы. Но ни то, ни
другое не устраняет сам факт: в момент паузы или разделения сети продлить
лок физически невозможно, и окно двойного исполнения существует.

PostgreSQL advisory lock в этом смысле не лучше: он тоже не переживает
сетевое разделение между приложением и базой корректно с точки зрения
«гарантированно только один держатель» — при обрыве TCP сессия и вместе с
ней лок закрываются на стороне Postgres, но приложение может какое-то время
не знать об этом и продолжать считать себя владельцем.

**Настоящая гарантия «эта работа выполнена ровно один раз» в проекте — не
лок, а идемпотентность через `processed_events` (fencing по `event_id`)**:
обработчик проверяет по первичному ключу, обработано ли уже это конкретное
событие, и это единственный механизм, который остаётся корректным при любом
сочетании сбоев, потому что он не полагается на живость какого-либо
процесса или соединения — только на состояние, уже зафиксированное в базе.
Redis-лок в этой картине — предохранитель от «типичного» случая (два
консьюмера читают дублирующееся сообщение почти одновременно, TTL и
watchdog устроены с запасом), который экономит CPU и сеть в подавляющем
большинстве случаев, но не то, на чём держится корректность.

## Последствия

**Хорошее.** Лок не конкурирует за пул соединений `pkg/dbx`, живёт с явным и
настраиваемым TTL независимо от способа обрыва процесса, использует ту же
инфраструктуру (`pkg/redisx`), что и остальные Redis-паттерны фазы 2.

**Плохое.** Лок — это ещё один компонент (Redis) в списке зависимостей,
недоступность которого нужно учитывать: если Redis лёг, thumbnail-worker
либо не берёт лок вообще (и рискует параллельной обработкой), либо
блокируется на попытках его взять — решение об этом принимает вызывающий
код в thumbnail-worker, а не `pkg/redisx`.

**Риск, который нельзя убрать кодом.** Двойное исполнение работы под локом
теоретически возможно при сетевом разделении или паузе GC дольше TTL. Это
не баг реализации — это свойство любого лока с TTL поверх ненадёжной сети,
включая advisory lock. Единственный правильный ответ — не полагаться на лок
как на гарантию, а сделать саму работу под локом идемпотентной. thumbnail-
worker обязан быть написан так, чтобы повторная генерация превью для уже
обработанного `event_id` была безопасным no-op, а не катастрофой, которую
предотвращает лок. Лок в этой схеме — оптимизация производительности, а
`processed_events` — гарантия корректности; их нельзя перепутать местами.

**Что это НЕ означает.** Решение не запрещает advisory lock в принципе —
для сценария, где лок обязан жить строго в рамках одной транзакции и
сниматься автоматически при её завершении (например, сериализация миграций
между несколькими репликами `tools/automigrate`), advisory lock остаётся
уместным инструментом. Здесь фиксируется выбор конкретно для
thumbnail-worker, а не общий запрет.
