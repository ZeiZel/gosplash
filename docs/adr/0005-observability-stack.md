# ADR 0005. Jaeger заменяется на OTel Collector + Tempo/Loki/Prometheus/Grafana

- **Статус:** принято, 2026-09-12
- **Фаза:** 0

## Контекст

В репозитории был поднят Jaeger v2, принимающий OTLP напрямую. Отдельный
коллектор не требовался, контейнер был один, порт один — проще некуда. Ни один
сервис при этом в него ничего не слал: трассировка существовала только в
docker-compose.

Спецификация (§9) требует большего:

- метрики Prometheus на `/metrics` в каждом сервисе, RED для HTTP/gRPC, лаг
  Kafka, `outbox_pending`, hit ratio Redis, пул PostgreSQL;
- трейсы через OTel Collector в Tempo, со спанами HTTP, gRPC, GORM, go-redis
  и Kafka, с `traceparent` в заголовках сообщений;
- логи `slog` JSON с `trace_id`/`span_id` в Loki, с переходом из Grafana по
  `trace_id`;
- дашборд «gosplash overview» и правила алертов.

Jaeger закрывает из этого списка ровно один пункт — трейсы. Остальное пришлось
бы ставить рядом, и тогда Jaeger остаётся четвёртым UI, в который надо
переключаться вручную, теряя контекст.

## Решение

Собрать полный стек из четырёх сигналов под одной Grafana:

| Компонент | Роль | Порт с хоста |
|---|---|---|
| otel-collector | единственная точка приёма телеметрии (OTLP) | 54317 / 54318 |
| tempo | хранилище трейсов | 53200 |
| prometheus | метрики, pull с `/metrics` сервисов | 59090 |
| loki + promtail | логи | 53100 |
| grafana | одно окно, переходы между сигналами | 53000 |

Два решения внутри, которые стоит проговорить отдельно.

**Метрики идут pull'ом, мимо коллектора.** Сервис поднимает `/metrics` на
служебном порту (82xx), Prometheus приходит сам. Причина: при pull-модели сам
факт успешного скрейпа означает, что процесс жив и отвечает, — это бесплатная
проверка, которой при push нет. Коллектор при этом остаётся точкой приёма
только для трейсов, и это нормально: он развязывает «куда шлёт сервис» и «где
это хранится».

**Служебный порт отдельный от публичного.** `/metrics` и `/debug/pprof`
не должны быть доступны снаружи — на служебный порт просто не выдают ingress.
Плюс профилировать нужно ровно тогда, когда основной сервер захлёбывается,
и очередь его хендлеров не должна этому мешать. Отсюда же правило: основной
роутер сервиса никогда не `http.DefaultServeMux`, потому что импорт
`net/http/pprof` регистрируется именно в нём.

## Последствия

**Хорошее.** Три перехода, ради которых всё и строилось, работают из коробки
и настроены файлами в `deploy/observability/grafana/provisioning`:

- метрика → трейс: через exemplar'ы Prometheus;
- трейс → логи: Grafana собирает запрос в Loki по `trace_id` из спана;
- лог → трейс: `trace_id` в строке лога подсвечивается как ссылка.

Последние два работают только потому, что `pkg/otelx` подмешивает `trace_id`
в каждую строку `slog`. Без этого связка распадается, и стек превращается в
три независимых инструмента.

**Плохое.** Вместо одного контейнера теперь шесть, и `make up` стал тяжелее
(суммарно порядка 600 МБ образов и заметно больше памяти). Для ноутбука это
ощутимо; частичный ответ — `make up-obs`, которая поднимает наблюдаемость
отдельно, и возможность не поднимать её вовсе: при пустом
`OTEL_EXPORTER_OTLP_ENDPOINT` сервисы работают без трассировки.

**Что пришлось настроить руками и почему это стоило того.** Пять конфигов в
`deploy/observability/`. Их можно было бы заменить готовым `docker-compose` из
интернета, но тогда пропал бы смысл: половина учебной ценности здесь — в том,
что видно, откуда Prometheus берёт targets, почему Loki индексирует только
метки и что именно делает `batch`-процессор коллектора.

**Порт Jaeger 56686 освобождается.** Упоминания в README, Makefile и `TODO.md`
убраны в том же коммите, чтобы не оставлять ссылок на несуществующий UI.

**Следующий шаг, который здесь не делается.** Prometheus скрейпит сервисы по
статическому списку `host.docker.internal:82xx`, потому что сервисы
запускаются на хосте через `go run`. Когда в фазе 6 они переедут в Kubernetes,
статический список сменится на service discovery, а `deploy/helm` добавит
аннотации для скрейпа.
