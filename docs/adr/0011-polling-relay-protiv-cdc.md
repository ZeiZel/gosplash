# ADR 0011. Polling-relay против Debezium/CDC

- **Статус:** принято, 2026-09-12
- **Фаза:** 1

## Контекст

`pkg/outbox.Relay` (docs/adr/0008-*) публикует накопленные события, опрашивая
таблицу `outbox` по таймеру (`PollInterval`, по умолчанию 2с):
`SELECT ... WHERE published_at IS NULL ... FOR UPDATE SKIP LOCKED`. Это не
единственный способ реализовать relay в паттерне transactional outbox.

Альтернатива — **Change Data Capture**: читать не саму таблицу, а поток
изменений WAL PostgreSQL (`wal_level=logical`, тот же механизм, которым в
проекте уже пользуется логическая репликация `catalog` — `pg-catalog` →
`pg-catalog-replica`, см. `deploy/compose/postgres.yml`). Типовая реализация
— Debezium (Kafka Connect коннектор) с **Outbox Event Router SMT**
(single message transform), который читает `INSERT`'ы в `outbox` из WAL и
публикует их в целевые топики напрямую, вообще без отдельного relay-процесса
и без таблицы как «очереди ожидания».

## Решение

В фазе 1 остаёмся на polling-relay. CDC — сознательно отложенный следующий
шаг, а не путь, который не рассматривался.

Причины остаться на поллинге СЕЙЧАС:

- **Меньше движущихся частей.** CDC через Debezium требует Kafka Connect
  (свой кластер или `Debezium Server`), собственного мониторинга лага
  коннектора и настройки `wal_level=logical` НА КАЖДОЙ базе-источнике
  outbox — сейчас это только `pg-catalog` (ради read-реплики), а `media`
  (оба шарда), `wallet` и `order` этот режим WAL не используют вовсе.
  Включить его везде — не бесплатная операция: `wal_level=logical`
  увеличивает объём WAL и требует слотов репликации, за которыми нужно
  следить (заполнение диска, если слот перестал вычитываться).
- **Объём трафика фазы 1 не оправдывает эту сложность.** Задержка в
  `PollInterval` (2с) плюс время батча — не проблема для учебного стенда;
  преимущество CDC (события почти в реальном времени, без пустых SELECT
  при неактивном outbox) проявляется на объёме и SLA, которых здесь нет.
- **Явный код лучше скрытого коннектора** для целей проекта: `pkg/outbox`
  весь — на виду, в Go, с комментариями, объясняющими SKIP LOCKED и работу
  с шардами. Debezium — готовый чёрный ящик с собственным DSL
  конфигурации; для учебных целей это МЕНЬШЕ материала, а не больше.

## Последствия

**Хорошее.** Решение не закрывает путь к CDC — оно явно совместимо с ним
по контракту. `Relay` читает таблицу `outbox` СО ЗНАКОМОЙ Debezium'у формой
(`Outbox Event Router` ожидает ровно такую таблицу: id, aggregate_id, topic,
key/headers, payload). Замена реализации ограничена ГРАНИЦЕЙ публикации:
консьюмеры по-прежнему читают `Envelope` из тех же топиков и не заметят
разницы, кто именно их туда положил — `pkg/outbox.Relay` или Debezium.
Метрика `outbox_pending` при переходе на CDC теряет смысл (нет больше
таблицы-очереди со «ждущими» строками в привычном виде) и заменяется лагом
коннектора — это единственная точка наблюдаемости, которую придётся
пересобрать.

**Чем платим, оставаясь на поллинге.**

- **Задержка, привязанная к `PollInterval`.** Событие ждёт до 2 секунд
  (плюс обработка батча), прежде чем окажется в Kafka — для сценариев
  «увидеть публикацию мгновенно» это ощутимо.
- **Постоянная нагрузка на Postgres от пустых опросов.** Каждые
  `PollInterval` секунды `Relay` выполняет `SELECT count(*)` (метрика) и
  транзакцию с `SELECT ... FOR UPDATE SKIP LOCKED`, даже когда outbox
  пуст. Для одного relay и индексированного запроса это дёшево, но
  «дёшево» — не «бесплатно», и при большом числе сервисов с собственными
  relay это уже заметная фоновая нагрузка на кластер баз.
- **Задержка публикации растёт вместе с размером батча и числом шардов**
  (`docs/adr/0002-*`): `Relay` обходит шарды ПОСЛЕДОВАТЕЛЬНО в рамках
  одного тика (см. комментарий `pollAllShards` в `relay.go`) — при
  большом количестве шардов это стоило бы распараллелить, чего сейчас
  сознательно не делаем (нет цифр, доказывающих необходимость,
  `docs/adr/0006-*`).

**Путь миграции, если CDC понадобится:** поднять Kafka Connect (или
Debezium Server), включить `wal_level=logical` на нужных базах, настроить
Outbox Event Router SMT на таблицу `outbox`, остановить `Relay.Run` для
migrируемого сервиса. Схема таблицы (`OutboxRow`) уже совместима — миграция
не требует правки записывающей стороны (`outbox.Write` не меняется вовсе),
меняется только то, что читает таблицу и публикует из неё.
