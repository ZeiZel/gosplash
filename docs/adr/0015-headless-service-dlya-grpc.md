# ADR 0015. Headless Service для gRPC: почему обычный Service плохо балансирует HTTP/2

- **Статус:** принято, 2026-09-12
- **Фаза:** 3

## Контекст

Фаза 3 добавляет межсервисные gRPC-вызовы: catalog → wallet (резерв/списание
денег), order → catalog и order → wallet (шаги саги), а в перспективе —
любой сервис → любой сервис. Все они будут разворачиваться в Kubernetes с
несколькими репликами на под (Helm-чарт — фаза 6, но клиентский код,
который будет ходить в эти реплики, пишется уже сейчас, в `pkg/grpcx.Dial`).

Обычная практика для HTTP — поставить перед репликами `Service` типа
`ClusterIP` и не думать о балансировке вообще: `kube-proxy` сам раскидывает
TCP-соединения по подам через iptables/IPVS. Это же было сделано в фазе 0
для `media` и `catalog`. Возникает соблазн сделать то же самое для gRPC.

Проблема в том, ЧТО именно балансирует `kube-proxy`: он балансирует
**TCP-соединения**, выбирая под один раз, в момент установления
соединения. Для обычного HTTP/1.1-клиента, который на каждый запрос (или
на каждые несколько запросов, пока жив keep-alive) открывает новое
соединение, это нормально — каждое новое соединение снова проходит через
балансировку и может попасть в другой под.

gRPC работает поверх HTTP/2, а HTTP/2 намеренно ДЕРЖИТ ОДНО СОЕДИНЕНИЕ
ДОЛГО и мультиплексирует в нём произвольное количество запросов
одновременно — это одна из причин, почему HTTP/2 вообще был придуман
(избавиться от накладных расходов на установление соединения per-request).
gRPC-клиент в `pkg/grpcx` тоже открывает соединение один раз при `Dial`
и держит его: см. keepalive-настройки, рассчитанные именно на
долгоживущее соединение.

Следствие: если поставить перед gRPC-репликами обычный `ClusterIP`,
`kube-proxy` выберет ОДИН под в момент, когда клиент открывает соединение,
и ВСЕ запросы этого клиента, сколько бы их ни было, уйдут в этот один под,
пока соединение не порвётся. При трёх репликах `wallet` результат — вся
нагрузка `catalog` на одной реплике `wallet`, а две другие простаивают.
Хуже того, если у клиента несколько инстансов (несколько подов `catalog`),
каждый из них при старте откроет своё соединение и попадёт в свой под —
распределение получится случайным и негарантированным, а не равномерным.

## Решение

Для каждого gRPC-сервиса заводится `headless Service`
(`clusterIP: None`) вместо обычного `ClusterIP`, и `pkg/grpcx.Dial`
включает `round_robin` как service config по умолчанию
(`grpc.WithDefaultServiceConfig` в `client.go`).

Механика:

1. У headless Service нет единого виртуального IP. DNS-запрос к его имени
   (`wallet.rent-platform-dev.svc.cluster.local`) возвращает НЕ один IP
   балансировщика, а **A-записи всех Pod'ов** сервиса напрямую.
2. Встроенный DNS-резолвер `grpc-go` (используется по умолчанию для
   схемы `dns:///`, в которую по умолчанию разворачивается голый
   `host:port`) получает этот список адресов и передаёт его балансировщику
   соединения.
3. Политика `round_robin` открывает **отдельное HTTP/2-соединение к
   КАЖДОМУ адресу** из списка и распределяет исходящие RPC между ними по
   кругу.
4. Резолвер периодически (и по сигналу ошибки соединения) переспрашивает
   DNS — так список адресов остаётся актуальным, когда поды пересоздаются.

Итог: балансировка происходит НЕ на уровне TCP-соединения (как у
`kube-proxy`), а на уровне отдельного RPC-вызова — то есть именно там, где
для мультиплексирующего HTTP/2 она имеет смысл.

### Почему round_robin, а не что-то умнее (least_request, weighted)

`grpc-go` из коробки предлагает `round_robin` и более простой
`pick_first`. Для учебного стенда с равноценными репликами без разницы в
нагрузке `round_robin` — минимально достаточное решение: оно уже
устраняет главную проблему (весь трафик в один под) и не требует
дополнительной инфраструктуры (в отличие от `least_request`, для которого
нужна работающая обратная связь по латентности, а её проще всего получить
через service mesh — вне объёма проекта, см. §7 `docs/PLAN.md`).

## Последствия

**Хорошее.** Нагрузка от каждого клиента размазывается по всем репликам
целевого сервиса без внешнего балансировщика и без sidecar'а — chr `Dial`
и headless Service решают задачу вдвоём, каждый своей половиной (резолвинг
адресов — Kubernetes DNS, распределение вызовов — `grpc-go`).

**Плохое: клиент должен уметь резолвить и следить за изменениями endpoints.**
Вся балансировка теперь — обязанность КЛИЕНТСКОЙ библиотеки, а не
инфраструктуры. Если клиент написан не на `grpc-go` (или на старой его
версии без поддержки `round_robin`/DNS-резолвера) — он честно откроет
одно соединение к первому адресу из списка и будет ходить в один под,
даже не заметив проблемы. Это ровно то тихое поведение, из-за которого
ADR вообще понадобился: обычный `ClusterIP` "просто работает" на вид,
пока не измеришь распределение нагрузки по подам, а headless Service
"просто работает" только для клиента, который реализует балансировку
сам.

**Плохое: задержка реакции на скейлинг ограничена DNS-кэшем.**
`grpc-go` не подписывается на изменения списка адресов push'ем — он
периодически переопрашивает DNS (интервал переопроса — внутренняя деталь
резолвера, порядка десятков секунд, плюс TTL самой DNS-записи). Когда
`wallet` скейлится с 3 реплик до 6, новые поды не получат трафик
мгновенно — какое-то время (до следующего переопроса) клиенты продолжат
слать запросы только старым трём. Симметрично при скейл-down: под,
который Kubernetes уже удалил, ещё какое-то время может оставаться в
списке адресов клиента, и часть запросов будет попадать в закрытое
соединение — отсюда важность `grpc.GracefulStop` на сервере (см.
`pkg/grpcx.Shutdown`) и retry на клиенте (`pkg/resilience`): именно эта
пара забирает на себя запросы, которые прилетели в под, который уже
не должен их получать.

**Риск.** Headless Service без явного readiness-контроля отдаёт в DNS
ВСЕ поды, включая ещё не прошедшие readinessProbe (сам механизм
исключения "неготовых" адресов у headless Service работает иначе, чем у
`ClusterIP`, и должен быть проверен отдельно при написании Helm-чарта в
фазе 6). До тех пор часть трафика в момент раскатки новой версии может
на короткое время попадать в под, который ещё не готов принимать
запросы — смягчается тем же retry на стороне клиента.

**Что это НЕ означает.** Решение не отменяет обычный `ClusterIP` для
HTTP-портов тех же сервисов (`media`, `catalog`) — там балансировка на
уровне TCP-соединения устраивает: HTTP/1.1-клиенты (браузер, NGINX)
не держат одно соединение вечно так, как это делает gRPC-клиент. У
одного и того же сервиса может быть `ClusterIP` на HTTP-порт и headless
на gRPC-порт одновременно.
