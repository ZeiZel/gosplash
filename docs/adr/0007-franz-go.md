# ADR 0007. franz-go как клиент Kafka — против sarama и kafka-go

- **Статус:** принято, 2026-09-12
- **Фаза:** 1

## Контекст

Фаза 0 использовала `github.com/twmb/franz-go` без явного решения — просто
взяли работающую библиотеку для одного консьюмера и одного продюсера без
ретраев и DLQ. Фаза 1 требует от клиента заметно больше:

- ручное управление ребалансом (`BlockRebalanceOnPoll` + горутина на
  партицию, docs/PLAN.md 1.2) — чтобы одно медленное или битое сообщение
  не останавливало всю партицию, а партиции обрабатывались независимо;
- `PauseFetchPartitions`/`ResumeFetchPartitions` — способ, которым
  `RetryConsumer` ждёт `retry_at`, не блокируя остальные партиции своим же
  главным циклом (docs/adr/0010-*);
- административный запрос лага consumer group (`kafka_consumer_lag`) без
  парсинга вывода `kafka-consumer-groups.sh`;
- заголовки записи (`kgo.RecordHeader`) как в чтении, так и в записи —
  весь конверт (docs/adr/0003-*) держится на `event_id`/`event_type`/
  `traceparent` именно в заголовках;
- тонкий контроль гарантий продюсера: `RequiredAcks`, компрессия,
  `RecordDeliveryTimeout`, `RecordRetries`.

Три реалистичных варианта для Go в 2026 году:

| | `IBM/sarama` | `segmentio/kafka-go` | `twmb/franz-go` |
|---|---|---|---|
| Управление ребалансом | callback'и есть, но без штатного «отложить ребаланс до готовности» — аналог `BlockRebalanceOnPoll` пришлось бы собирать вручную поверх примитивов пониже уровнем | группового консьюмера с ручным ребалансом в духе `BlockRebalanceOnPoll` нет: `ConsumerGroup` абстракция скрывает партиции целиком, `Reader` без группы требует ручного управления офсетами с нуля | `BlockRebalanceOnPoll` — штатная опция, схема goroutine-per-partition — задокументированный пример библиотеки |
| Pause/resume партиций | есть, но ниже уровнем и меньше документирована | нет прямого аналога у групповых `Reader` | `PauseFetchPartitions`/`ResumeFetchPartitions` — штатный API |
| Административный клиент | `sarama.ClusterAdmin`, лаг считать вручную по офсетам | нет официального аналога `kadm` | `kadm` — официальный подпакет, `Client.Lag` считает лаг группы одним вызовом |
| Идемпотентный продюсер | есть | ограниченная поддержка | включён по умолчанию |
| Заголовки записи | есть | есть (начиная с относительно поздних версий) | есть, первоклассная часть API с самого начала |
| Активность разработки | поддерживается (IBM), но осторожно, без резких изменений API | заметно снизившийся темп разработки | активная разработка, кодовая база моложе и написана с оглядкой на уроки sarama |

## Решение

Остаёмся на `twmb/franz-go` (и его официальном подпакете `kadm` для лага).
Причина не «оно уже было», а то, что ключевые механизмы фазы 1 —
`BlockRebalanceOnPoll` + горутина на партицию и `PauseFetchPartitions` для
`RetryConsumer` — у franz-go являются задокументированными, официально
поддерживаемыми частями API, а не самодельной надстройкой поверх более
низкоуровневых примитивов sarama или kafka-go. Меньше кода, которому потом
приходится доверять как собственному.

## Последствия

**Хорошее.** Код `pkg/kafkax` (engine.go, retry.go, lag.go) написан ПРОТИВ
задокументированного поведения библиотеки, а не против его реконструкции
по исходникам — при обновлении версии franz-go есть на что сослаться
в changelog'е.

**Чем платим.**

- **Меньшее комьюнити.** У sarama на порядок больше Stack Overflow-ответов
  и статей «как я мигрировал с Zookeeper на KRaft на sarama» — отладка
  редкого краевого случая скорее потребует чтения исходников franz-go, чем
  поиска готового ответа.
- **Фактор автобуса.** franz-go — по факту проект одного основного
  мейнтейнера (twmb). Библиотека качественная и активно используется в
  проде рядом компаний, но это не IBM-поддерживаемый sarama с формальными
  гарантиями сопровождения.
- **Широкий API — длиннее кривая обучения.** `kgo.Opt`/`ProducerOpt`/
  `ConsumerOpt`/`GroupOpt` — десятки функций-опций, и не все комбинации
  очевидны (например, `BlockRebalanceOnPoll` без парного
  `AllowRebalance()` в каждой итерации `Run` тихо вешает ребаланс
  навсегда — ни ошибки, ни паники, просто новый инстанс группы никогда
  не получит партиции).
- **Меньше проверено «в бою» на экстремальных масштабах**, чем sarama,
  которая эксплуатируется дольше и в более широком спектре нагрузок.

Ничего из этого не является причиной уйти с franz-go в текущем проекте:
для учебного стенда с одним брокером и умеренной нагрузкой перечисленные
риски не материализуются, а выигрыш в ясности кода (`BlockRebalanceOnPoll`,
`kadm`, `PauseFetchPartitions` из коробки) больше, чем цена. При росте
проекта до уровня, где нужны формальные SLA на клиентскую библиотеку
и её поддержку, стоит переоценить это решение — но не раньше.
