# Runbook: отставание реплики каталога

## Симптом

- `make replication` (или `GET /catalog/replication`) показывает
  `lag_rows` заметно больше нуля и не убывающий.
- Пользователи видят на карточке/в ленте (читается с реплики,
  `pg-catalog-replica`) устаревшие данные по сравнению с тем, что только
  что было записано (primary).

## Что это значит

Репликация `pg-catalog` → `pg-catalog-replica` в этом проекте **логическая**
(`docs/PLAN.md`, §0: `CREATE PUBLICATION`/`CREATE SUBSCRIPTION`, настраивается
`tools/automigrate`), не потоковая (streaming). Ключевое отличие для
диагностики: реплика — обычная ЗАПИСЫВАЕМАЯ база с собственным процессом
применения изменений (`logical replication worker`), а не побайтовая копия
WAL. Значит, лаг может быть вызван либо публикующей стороной (primary не
успевает генерировать/держать WAL), либо ПОДПИСЫВАЮЩЕЙ (реплика не успевает
ПРИМЕНЯТЬ полученные изменения) — это разные причины с разными симптомами.

## Что делать

**1. Измерить лаг с двух сторон:**

```bash
make replication
```

Это печатает: `primary_rows`/`replica_rows` (через API сервиса,
`dbresolver`), то же самое напрямую через `psql` в обеих базах, и состояние
подписки `pg_stat_subscription` (`subname`, `running`, `received_lsn`,
`latest_end_lsn`) — читай именно `pg_stat_subscription`, счётчик строк
может на секунду разойтись просто из-за момента снятия замера.

**2. Подписка вообще запущена?**

Если `running` в выводе `pg_stat_subscription` — `false` (или строка вообще
отсутствует) — worker логической репликации не поднят. Частые причины в
локальном окружении:

- `pg-catalog-replica` был пересоздан (`make nuke` / удалённый volume) без
  повторного `make migrate-catalog` — подписка создаётся миграцией, не
  автоматически при старте контейнера;
- primary был перезапущен с ДРУГИМ содержимым `pg_hba.conf`/паролем — редко
  в этом compose (пароль фиксирован), но проверь `docker compose logs
  pg-catalog-replica` на ошибки аутентификации репликации.

Чинится через:

```bash
make migrate-catalog     # ONLY=catalog — пересоздаёт публикацию/подписку идемпотентно
```

**3. Подписка запущена, но `received_lsn` растёт медленнее, чем пишет primary.**

Значит, узкое место — САМА реплика: она получает изменения, но не успевает
их закоммитить. Проверь, не создан ли на реплике лишний индекс/триггер,
которого нет на primary (в логической репликации схему реплики ведёшь ты
сам, `tools/automigrate` не гарантирует идентичность автоматически — DDL
НЕ реплицируется), и не идёт ли на реплике параллельная тяжёлая нагрузка
(в проде — например, аналитический запрос, который блокирует применение
изменений).

**4. `received_lsn` не растёт вообще, хотя primary активно пишет.**

Проблема на стороне СЕТИ или PUBLICATION на primary — проверь `docker
compose logs pg-catalog` на ошибки WAL sender, и что `wal_level=logical`
всё ещё выставлен (`deploy/compose/docker-compose.postgres.yml`: `command: postgres -c
wal_level=logical` — если кто-то поднял `pg-catalog` БЕЗ этого флага,
публикация физически не может писать нужный объём в WAL).

Если сеть до primary искусственно замедлена (`deploy/chaos/slow-pg.sh
pg-catalog`) — это ОЖИДАЕМАЯ причина роста лага, а не инцидент: сними
задержку и жди возврата к норме, не диагностируй дальше.

## Как убедиться, что починилось

```bash
make replication
```

`lag_rows` должен вернуться к небольшому, стабильно малому значению (не
обязательно 0 — логическая репликация асинхронна по определению, полностью
нулевой лаг означает только "в этот конкретный момент primary ничего не
писал"). `pg_stat_subscription.received_lsn` должен приближаться к
`latest_end_lsn` primary и не отставать систематически. Прогони
`make feed` — только что записанная на primary карточка обязана появиться
в ответе (он идёт с реплики) в разумное время после публикации.
