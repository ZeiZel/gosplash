# Runbook: `outbox_pending` растёт

Алерт: `OutboxBacklog` (`deploy/observability/alerts.yaml`) —
`outbox_pending > 100` в течение 5 минут, метка `service` — чей outbox.

## Симптом

- Алерт `OutboxBacklog` в Prometheus (`make alerts`).
- Grafana, дашборд «gosplash overview», панель «Очередь outbox» — график
  растёт и не возвращается к нулю.
- `make media-outbox` показывает растущее "не отправлено" на одном или
  обоих шардах.

## Что это значит

Строка в `outbox` (`docs/adr/0008-*`) появляется в ОДНОЙ транзакции с
бизнес-изменением (см. `pkg/outbox`), поэтому сам факт роста `outbox_pending`
**не означает потерю данных** — это буквально весь смысл паттерна: событие
уже надёжно на диске, просто ещё не уехало в Kafka. Три причины роста:

1. **Relay не запущен.** Relay — часть процесса сервиса (media), не
   отдельный демон — если `run-media` не поднят, `outbox_pending` растёт
   с той же скоростью, с какой идут загрузки, и не снижается вообще.
2. **Kafka недоступна.** Relay видит ошибку публикации, логирует её и НЕ
   помечает строку `published_at` — попробует снова на следующем тике
   (`OUTBOX_POLL_INTERVAL`, по умолчанию 1с). Это ШТАТНОЕ поведение при
   недоступности Kafka (см. `deploy/chaos/kill-kafka.sh` — тот же сценарий,
   вызванный намеренно) — не инцидент сам по себе, если Kafka скоро вернётся.
3. **Relay работает, но не успевает.** Партия `OUTBOX_BATCH_SIZE` (по
   умолчанию 100) обрабатывается медленнее, чем строки добавляются —
   реже встречается, обычно означает саму Kafka под нагрузкой (высокий
   `RecordDeliveryTimeout`) или сеть до брокера.

## Что делать

```bash
make media-outbox        # "не отправлено" по каждому шарду media
```

Помни про ADR 0002 (docs/adr/0002-*): у media СВОЙ outbox НА КАЖДОМ ШАРДЕ,
relay обходит оба — растущее число на ОДНОМ шарде и нормальное на другом
уже сужает причину до конкретной базы/сети, а не до Kafka целиком.

**Проверь, жив ли сам relay** (косвенно — жив ли процесс media вообще):

```bash
curl -s http://localhost:58080/media/readyz | jq .checks
```

Если `/readyz` не отвечает совсем — media не запущен, поднимай:
`make run-media`.

**Проверь доступность Kafka:**

```bash
make doctor              # секция "kafka OK/FAIL"
```

Если Kafka недоступна — это `docs/runbooks/kafka-lag.md` косвенно, но
сначала верни саму Kafka (см. `deploy/chaos/kill-kafka.sh` header — та же
логика восстановления: `docker compose start kafka`, дождаться
`kafka-broker-api-versions.sh`).

**Если Kafka жива, relay жив, а `outbox_pending` всё равно растёт** —
смотри логи на предмет ошибок публикации, отличных от "недоступна":

```bash
make logs-loki C=media
```

Частая причина здесь — не сама Kafka, а конкретный топик (например, ACL,
если она когда-нибудь появится) или `RecordDeliveryTimeout` слишком узкий
для текущей сетевой задержки (см. `deploy/chaos/slow-pg.sh` — аналогичный
чек для БД, но тот же принцип: сначала измерь задержку, потом трогай таймаут).

## Как убедиться, что починилось

```bash
make media-outbox
```

"не отправлено" должно СХОДИТЬ К НУЛЮ в течение нескольких
`OUTBOX_POLL_INTERVAL` после устранения причины — без перезапуска процесса
media и без ручного вмешательства в таблицу `outbox`. Проверь также, что то,
что накопилось ВО ВРЕМЯ инцидента, реально доехало до каталога:

```bash
make feed
```

Алерт `OutboxBacklog` гаснет через `for: 5m` после того, как метрика
опустится ниже порога — не считай инцидент закрытым раньше этого времени,
даже если график на глаз уже выглядит нормально.

Если "не отправлено" НЕ убывает несмотря на живую Kafka и живой relay —
не трогай таблицу `outbox` руками (`UPDATE ... SET published_at = now()`
соврёт метрике, но НЕ доставит событие) — это симптом бага в самом relay,
заводи инцидент по коду, а не лечи цифру.
