# Runbook: растёт лаг Kafka-консьюмера

Алерт: `KafkaConsumerLag` (`deploy/observability/alerts.yaml`) —
`kafka_consumer_lag > 1000` в течение 5 минут.

## Симптом

- Алерт `KafkaConsumerLag` горит в Prometheus (`make alerts`).
- В Grafana (дашборд «gosplash overview», панель «Отставание консьюмеров»)
  график лага растёт и не возвращается к нулю.
- Пользователи видят карточки каталога с опозданием после загрузки фото
  (catalog) или без превью (thumbnail-worker).

## Что это значит

Консьюмер читает `media.photo.uploaded` (catalog, thumbnail-worker) или
`.retry`-топики МЕДЛЕННЕЕ, чем продюсер пишет. Три разные причины дают
одну и ту же метрику — не лечи наугад, сначала пойми, какая именно:

1. **Консьюмер не запущен / упал.** Лаг растёт линейно с нуля, без единой
   обработки. Самая частая причина в учебном окружении — забыли
   `make run-catalog` / `make run-thumbs` после рестарта.
2. **Консьюмер жив, но не успевает.** Обработка одного сообщения занимает
   слишком долго (gRPC до media подвис, PostgreSQL под нагрузкой) —
   лаг растёт, но `kafka_messages_processed_total` тоже растёт, просто
   медленнее прироста в топике.
3. **Ребаланс застрял.** После падения одного из нескольких инстансов
   partitions какое-то время не назначены никому — временный скачок лага,
   который должен сам сойти на нет за секунды (см. `pkg/kafkax`:
   `OnPartitionsAssigned/Revoked` в логах).

## Что делать

```bash
make consumer-lag                 # CLI-срез + та же метрика из Prometheus
```

Смотри на КОНКРЕТНУЮ группу/партицию, у которой растёт `LAG`, а не на
агрегат — это сразу отсекает часть гипотез (одна партиция vs все).

**Если консьюмер не запущен** (`make groups` не показывает группу, или в
`make consumer-lag` для неё "группа ещё не создана"):

```bash
make run-catalog          # или run-thumbs — смотря чья группа
```

**Если консьюмер жив, но лаг растёт** — проверь, на чём именно он стоит:

```bash
make logs-loki C=catalog          # C=thumbnail-worker для второго случая
```

Ищи повторяющиеся ошибки в логе (таймауты gRPC в media, ошибки PostgreSQL).
Если причина — перегруженный downstream (media, PostgreSQL), лечи ЕГО, а не
консьюмер: искусственно ускорить чтение из Kafka, когда узкое место дальше
по цепочке, только откладывает проблему.

**Если похоже на застрявший ребаланс** (лаг подскочил СРАЗУ после падения
одного инстанса и не двигается больше минуты) — проверь, что у оставшихся
инстансов партиции действительно назначены:

```bash
make logs-loki C=catalog | grep -i "партиции"
```

Если партиции НИКОМУ не назначены дольше `session.timeout.ms` — это уже не
штатный ребаланс, а зависший процесс с той же consumer group ID, который
не отдаёт партиции (например, старый инстанс не убит до конца). Проверь
`ps` / `lsof -tiTCP:<порт>` на предмет осиротевших процессов.

## Как убедиться, что починилось

```bash
make consumer-lag
```

`LAG` должен монотонно убывать и дойти до значений, близких к нулю (не
обязательно ровно 0 — под постоянной нагрузкой всегда есть небольшой
"хвост" между записью продюсером и чтением консьюмером). В Grafana график
лага возвращается к базовой линии, алерт `KafkaConsumerLag` гаснет
(`for: 5m` — подожди эти 5 минут, прежде чем считать инцидент закрытым:
алерт специально не гаснет мгновенно на первом же низком значении).

Если лаг не убывает, а сообщения при этом действительно обрабатываются —
проверь DLQ (`docs/runbooks/dlq.md`). Само по себе битое сообщение партицию
не блокирует НАВСЕГДА (docs/adr/0010-*: permanent-ошибка сразу уходит в
DLQ, offset идёт дальше) — но КАЖДАЯ retryable-ошибка перед этим тратит
`CONSUMER_MAX_RETRIES` попыток НА МЕСТЕ (`.env`, по умолчанию 3), прежде чем
сообщение уйдёт в `.retry`-топик. Если таких сообщений много подряд, лаг
растёт не потому что "не успевает разбирать", а потому что каждое сообщение
стоит в разы дороже штатного — тогда чини источник ошибок (media/PostgreSQL),
а не сам консьюмер.
