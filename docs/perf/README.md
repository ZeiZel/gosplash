# Результаты нагрузочных прогонов

Сюда попадают РЕАЛЬНЫЕ числа с РЕАЛЬНОГО стенда — никогда не выдумываются
и не экстраполируются "на глаз". Если прогон не выполнялся, в этой папке
для него нет файла: пустое место честнее, чем правдоподобная выдумка.

## Статус на 2026-09-12

**Ни одного реального прогона на этой машине не выполнялось.** k6-сценарии
(`deploy/k6/*.js`) проверены иначе — синтаксически (`node --check`) и
логически (реально исполнены через `docker run grafana/k6` против
одноразового HTTP-мока, эмулирующего API media/catalog/order, см. отчёт по
задаче) — это подтверждает, что скрипты РАБОТАЮТ, но НЕ даёт ни одного
числа о реальной производительности gosplash: мок отвечал за микросекунды
и не содержал ни PostgreSQL, ни Kafka, ни Redis, ни Temporal. Числа в этой
папке появятся только после прогона `make k6-upload` / `make k6-catalog` /
`make k6-order` против поднятого `make up` + запущенных сервисов.

## Формат имени файла

```
docs/perf/ГГГГ-ММ-ДД-<сценарий>[-<вариант>].md
```

Примеры: `2026-09-15-catalog-read-warm.md`,
`2026-09-15-catalog-read-cold.md`, `2026-09-16-upload-burst.md`,
`2026-09-16-place-order.md`. Дата — день ПРОГОНА, не день коммита файла.
Для `catalog_read.js` варианты `warm`/`cold` — ОТДЕЛЬНЫЕ файлы (это два
разных прогона с разными числами, а не один файл с двумя колонками),
чтобы сравнение делалось явным `diff`, а не вычитыванием таблицы глазами.

## Обязательные поля результата

Шаблон — `docs/perf/TEMPLATE.md`, копируй его для каждого нового прогона.
Обязательные числа: **p50 / p95 / p99** (в миллисекундах), **RPS**
(запросов в секунду за время прогона), **дата и время прогона**, **что
было изменено** относительно предыдущего прогона того же сценария (новая
версия кода? другие пороги нагрузки? другое железо? "ничего, контрольный
повтор" — тоже валидный ответ, только напиши его явно, а не оставляй поле
пустым).

Число без даты бесполезно (нельзя понять, устарело или нет), число без
"что изменено" бесполезно ВДВОЙНЕ (нельзя понять, разница со следующим
прогоном — реальная регрессия или шум измерения).

## Как снять числа

Каждый k6-сценарий сам печатает JSON-сводку в конце прогона (`handleSummary`,
см. `deploy/k6/README.md`) и кладёт её в `summary-<сценарий>[-<режим>].json`
рядом с местом запуска — эти файлы переносятся В ТЕКСТ результата (как
цитата, не просто прикладываются как отдельные артефакты, чтобы результат
читался без похода за другим файлом):

```bash
make k6-catalog MODE=warm
make k6-catalog MODE=cold
# сравни p99 из двух summary-catalog-read-*.json — это и есть число,
# которое docs/PLAN.md называет критерием готовности фазы 2.
```

Во время прогона держи открытой Grafana (`http://localhost:53000`,
дашборд «gosplash overview») — раздел «Куда смотреть в Grafana» в
`deploy/k6/README.md` объясняет, какие панели с чем сверять. Если числа
k6 и Grafana расходятся заметнее, чем на сетевой путь k6→NGINX→сервис,
это стоит явно отметить в результате как аномалию, а не тихо взять число
поудобнее.

## Критерии готовности, которые эти числа обязаны подтвердить

Не измерение ради измерения — у каждого сценария есть конкретный порог
из `docs/PLAN.md`, который результат либо подтверждает, либо опровергает:

- **catalog_read (warm vs cold)** — фаза 2: разница p99 должна быть в разы,
  не в проценты (если её нет — кэш не подключён или TTL/размер горячего
  набора подобраны неверно, см. `deploy/k6/catalog_read.js`).
- **upload_burst** — фаза 2, п. 2.3: `rate_limited` (429) должен быть
  заметно больше нуля, `real_failures` (5xx) — около нуля.
- **place_order** — ADR 0018: `idempotency_violations` строго 0.

Результат, который не упоминает, подтверждён порог или нет, — неполный.
