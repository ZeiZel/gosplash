## Этап 1. Образец: «загрузка изображения» — **готово**

Одна фича, прошитая через весь стек. Дальше ты пишешь по её образу.

```
POST /media/upload
   │
   ├─► MinIO                      файл (байты в БД не попадают никогда)
   ├─► PostgreSQL шард 0 или 1    метаданные, шард = fnv32(user_id) % 2
   └─► Kafka: image.uploaded      тонкое событие: только идентификаторы
                │
                ▼
         catalog-consumer
                │
                ├─► gRPC media.GetImage(id, user_id)   подробности
                └─► PostgreSQL catalog primary          денормализованная карточка
                                    │ логическая репликация
                                    ▼
                             pg-catalog-replica  ◄── сюда идут все SELECT'ы
                                                     публичного API
```

Где что смотреть:

| Тема | Файлы |
|---|---|
| Контракты protobuf | `proto/media/v1/media.proto`, `proto/events/v1/events.proto` |
| gRPC-сервер | `services/media/internal/image/grpc.go` |
| gRPC-клиент | `services/catalog/internal/catalog/indexer.go`, `tools/mediactl` |
| Kafka: продюсер и консьюмер | `libs/pkg/kafka/kafka.go` |
| Публикация события | `services/media/internal/image/service.go` |
| Шардирование | `libs/pkg/db/db.go` → `Shards`, `services/media/internal/image/repository.go` |
| Репликация (роутинг чтений) | `libs/pkg/db/db.go` → `OpenWithReplica`, `services/catalog/internal/catalog/repository.go` |
| Репликация (настройка в SQL) | `services/catalog/migrations/auto.go` |
| Миграции всех баз | `tools/automigrate/cmd/main.go` |
| S3 | `libs/pkg/s3/s3.go` |

✅ Проверка: `make demo` — загрузит от четырёх пользователей, покажет
распределение по шардам, дёрнет media по gRPC, покажет ленту каталога
и отставание реплики.

Отдельные команды: `make shards`, `make feed`, `make replication`,
`make my-images U=3`, `make grpc-media ID=<uuid> U=1`,
`make topic-tail T=image.uploaded`, `make lag G=catalog-indexer`.

### Что стоит потрогать руками, прежде чем идти дальше

- [ ] Останови catalog, загрузи три картинки, запусти обратно — карточки
      доедут: Kafka хранит сообщения, консьюмер продолжит с последнего offset'а
- [ ] Запусти catalog в двух терминалах и посмотри в Kafka UI (58090), как
      шесть партиций разделились между процессами
- [ ] Загрузи одну картинку и сразу дёрни `make replication` — поймай момент,
      когда `lag_rows` не равен нулю
- [ ] Загрузи от пользователей 1..10 и посмотри `make shards`: распределение
      не будет ровным, и это нормально для хэша
- [ ] Убей media, загрузи через catalog… не выйдет — зато `make lag` покажет,
      как растёт отставание, пока консьюмер ретраит gRPC-вызов
- [ ] Открой `psql-shard0` и `psql-shard1`: одна и та же таблица `images`,
      непересекающиеся строки

### Что в этой фиче сделано нарочито просто

Это не недоделки, а следующие этапы. Список честный — чтобы ты знал, где
образец расходится с тем, как надо в проде:

- [ ] событие публикуется ПОСЛЕ коммита, а не через outbox: если Kafka лежит,
      картинка сохранится, а в каталог не попадёт (этап 2)
- [ ] у консьюмера нет retry-топика и DLQ: битое сообщение просто пропускается,
      временная ошибка ретраится бесконечно (этап 2)
- [ ] нет `processed_events`: идемпотентность держится только на том, что
      upsert безопасно повторить (этап 2)
- [ ] нет валидации, что загруженный файл — действительно изображение,
      и не считаются его размеры (этап 2, вместе с превью)
- [ ] нет аутентификации: пользователь берётся из заголовка `X-User-Id`
- [ ] `hash(user_id) % N` ломается при добавлении шарда (этап 5)
- [ ] нет ни кэша, ни трассировки (этапы 3 и 8)

## Этап 2. Kafka + outbox + thumbnail-worker

🎯 После загрузки автоматически появляются три превью, статус меняется на `ready`.

Продюсер, консьюмер и событие `ImageUploaded` уже есть — см. этап 1.
Здесь достраивается то, что там было сделано нарочито просто.

### 2.1 Контракты
- [x] `proto/events/v1/events.proto`, `libs/pkg/kafka` — сделано в этапе 1
- [ ] Добавить `ImageProcessed` и `ImageDeleted` рядом с `ImageUploaded`
- [ ] `make proto`, `make proto-lint` без замечаний

### 2.2 Outbox в media
Сейчас `service.Upload` публикует событие ПОСЛЕ коммита: упадёт Kafka —
картинка сохранится, а в каталог не попадёт. Лечится так:

- [ ] Таблица `outbox (id, aggregate_id, topic, payload, created_at, published_at)`
- [ ] Запись события и метаданных **в одной транзакции** `db.Transaction(...)`
- [ ] Relay-горутина: `SELECT ... WHERE published_at IS NULL FOR UPDATE SKIP LOCKED`,
      отправка в Kafka, простановка `published_at`
- [ ] Бонус: партиционировать outbox по дню и дропать старые партиции —
      таблица растёт быстро, а история отправленных событий не нужна

### 2.3 Воркер превью
- [ ] `thumbnail-worker`: читает `image.uploaded`, тянет оригинал из MinIO,
      делает small 320 / medium 800 / large 1600 в WebP, кладёт в `gosplash-thumbnails`,
      публикует `image.processed`
- [ ] Обновление статуса картинки на `ready` (сейчас она навсегда `uploaded`)
- [ ] Валидация: что файл действительно изображение, и вычисление width/height
- [ ] Идемпотентность: таблица `processed_events (event_id PK)`, вставка до обработки.
      В каталоге хватило upsert'а, здесь не хватит: сделать превью дважды —
      это лишняя работа и лишние объекты в S3
- [ ] Ретраи: при ошибке → `image.uploaded.retry` со счётчиком в заголовке,
      после N попыток → `image.uploaded.dlq`. Сейчас `libs/pkg/kafka` просто
      не двигает offset, и битое сообщение ретраится вечно

✅ Загрузи файл → `make topic-tail T=image.uploaded` показывает сообщение →
`make s3-tree B=gosplash-thumbnails` показывает три превью →
`make lag G=thumbnail-worker` показывает нулевое отставание.
Останови воркер, загрузи три файла, запусти воркер — все три должны обработаться.
Запусти воркер в двух терминалах и посмотри в Kafka UI, как партиции разделились между ними.

⚠️ Обработка изображений — CPU-bound. Не запускай горутину на каждое сообщение:
получишь тысячу параллельных ресайзов и упрёшься в память. Ограничь пул
размером `runtime.NumCPU()`.

⚠️ Не коммить offset до того, как работа сделана. Иначе падение воркера = потерянное
сообщение. Это разница между at-least-once и at-most-once, и её надо прочувствовать
руками: сделай специально «неправильно», убей воркер посередине, посмотри на результат.

🧠 Зачем outbox, если можно просто послать в Kafka после коммита (ответ: между коммитом
и отправкой процесс может умереть); почему exactly-once в общем случае недостижимо
и его заменяют «at-least-once + идемпотентность».

- [ ] `proto/catalog/v1/catalog.proto`: `GetImage`, `ListImages`, `Search` —

- [ ] Консьюмер `image.processed` → обновить карточку и сбросить кэш
- [ ] `libs/pkg/cache`: cache-aside поверх `go-redis`, ключи `catalog:image:{id}`
- [ ] `singleflight` вокруг похода в БД при промахе
- [ ] Refresh-ahead для топ-100: горутина обновляет ключи до истечения TTL
- [ ] Rate limiting загрузок: `INCR` + `EXPIRE` по `rl:upload:{user_id}`

✅ Первый `GET /catalog/images/{id}` идёт в БД, второй — нет: проверь через
`make redis-monitor` в соседнем терминале. `make redis-keys` показывает TTL.
`make redis-flush` → первый запрос снова медленный.

⚠️ TTL с точностью до секунды у тысячи ключей = синхронное протухание и залп в БД.
Добавляй джиттер: `ttl + rand(0, ttl/10)`.

🧠 Разница cache-aside / write-through / refresh-ahead и почему для ленты выбран
именно этот вариант; что такое cache stampede и почему `singleflight` его лечит,
а увеличение TTL — нет.

## Этап 4. Партиционирование `image_views`

🎯 Таблица просмотров, разрезанная по месяцам, и работающее удаление старых данных.

- [ ] `CREATE TABLE image_views (...) PARTITION BY RANGE (viewed_at)` в миграциях catalog
- [ ] Ключ партиционирования обязан входить в PRIMARY KEY — понять, почему
- [ ] Партиции на текущий и следующий месяц + функция «создать вперёд на N месяцев»
- [ ] Запись просмотра при `GetImage` (батчем через канал, не по одной строке)
- [ ] `DETACH PARTITION` + `DROP TABLE` для месяцев старше трёх

✅ `make pg-partitions` показывает список партиций. `EXPLAIN (ANALYZE)` на запросе
с фильтром по `viewed_at` должен показать `Partitions removed by pruning` —
это и есть весь смысл упражнения. Сравни план с фильтром по дате и без него.

🧠 Партиционирование ускоряет не всё подряд, а запросы с ключом партиционирования
в `WHERE`. Запрос без него станет медленнее — просканирует все партиции.
Главный выигрыш вообще не в скорости чтения, а в том, что удаление месяца данных
превращается из многочасового `DELETE` в мгновенный `DROP TABLE`.

## Этап 6. wallet + order: сага руками

🎯 Покупка лицензии работает, а при сбое на середине деньги не пропадают.
**Сначала руками**, без Temporal — иначе не будет видно, что именно он потом спрячет.

- [ ] `wallet`: `accounts`, `transactions`, gRPC `Reserve` / `Commit` / `Release` / `Payout`
- [ ] Все операции идемпотентны по `operation_id` — сага будет ретраить
- [ ] `order`: таблица `saga_instances` (`state`, `step`, `payload`, `compensations`)
- [ ] Шаги: `wallet.Reserve` → `catalog.CreateLicense` → `wallet.Payout` → `license.purchased`
- [ ] Компенсации в обратном порядке: `wallet.Release`, `catalog.RevokeLicense`
- [ ] Восстановление после падения: при старте добрать незавершённые саги из таблицы

✅ Успешный сценарий: баланс покупателя уменьшился, автора — вырос, лицензия есть.
Сценарий отказа: **выключи wallet перед третьим шагом** и убедись, что резерв снят,
лицензия аннулирована, а `saga_instances` показывает, где именно всё встало.
Убей order-service посередине саги и перезапусти — она должна доехать сама.

⚠️ Компенсация ≠ rollback. `Release` — это новая операция, а не откат старой.
Если между `Reserve` и `Release` покупатель успел потратить деньги, оба факта
останутся в истории — так и должно быть.

🧠 Почему у распределённой транзакции нет изоляции: чужой запрос увидит
промежуточное состояние. Прикинь, что это значит для показа баланса в UI.
