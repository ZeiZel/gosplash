# Chaos-скрипты (фаза 6)

Каждый скрипт ломает РОВНО ОДНУ вещь и печатает, что именно проверять после
этого — по образцу `docs/runbooks/`, только наоборот: runbook читают, когда
что-то сломалось само; эти скрипты ломают специально, чтобы проверить, что
защита действительно работает, а не только описана в ADR.

| Скрипт | Что ломаем | Какой паттерн проверяет | Ожидаемое поведение |
|---|---|---|---|
| `kill-kafka.sh` | останавливает контейнер `kafka` на N секунд | transactional outbox (docs/adr/0008-*) | media продолжает принимать загрузки, outbox копится, `/catalog/readyz` краснеет по Kafka, но процесс не падает; после подъёма всё доезжает без вмешательства человека |
| `kill-wallet.sh` | `kill -9` процессу wallet посреди саги | circuit breaker (pkg/resilience) + компенсирующие транзакции (сага) | вызовы в wallet проваливаются за миллисекунды (без TCP-таймаута) после размыкания breaker; если резерв успел случиться — сага компенсирует и деньги возвращаются после подъёма wallet |
| `kill-catalog.sh` | `kill -9` процессу catalog ДО размещения заказа | компенсирующие транзакции саги (docs/PLAN.md, критерий готовности фазы 3) | `GrantLicense` проваливается на всех ретраях, `RevokeLicense`/`ReleaseFunds` откатывают резерв денег — заказ уходит в `failed`, баланс покупателя не меняется |
| `slow-pg.sh` | сетевая задержка (`tc netem`) на путь к PostgreSQL | деградация зависимости без отказа (таймауты, пул соединений) | запросы к базе заметно медленнее, но не падают; `/readyz` может замигать, если задержка превысит его собственный таймаут пинга |

## Предпосылки

```bash
make up
make migrate
```

`kill-wallet.sh` и `kill-catalog.sh` дополнительно рассчитывают на запущенные
через `go run` сервисы (`make run-media`, `make run-catalog`, `make run-wallet`,
`make run-order`, `make run-worker`) — это ОБЫЧНЫЕ процессы на хосте, а не
docker-контейнеры (см. `deploy/nginx/gateway.conf`: gateway достаёт до них
через `host.docker.internal`), поэтому "уронить" их означает найти PID по
порту (`lsof`) и `kill -9`, а не `docker stop`. `kill-kafka.sh` и `slow-pg.sh`,
наоборот, работают с docker-контейнерами напрямую через
`docker compose -f deploy/compose/docker-compose.yml`.

## Запуск

```bash
./deploy/chaos/kill-kafka.sh [секунд_простоя]     # по умолчанию 30
./deploy/chaos/kill-wallet.sh [секунд_простоя]     # по умолчанию 15
./deploy/chaos/kill-catalog.sh                     # держит catalog мёртвым до конца сценария
./deploy/chaos/slow-pg.sh [контейнер]              # по умолчанию pg-catalog, DELAY=500ms
```

Или через `make` (`mk/load.mk`): `make chaos-kafka`, `make chaos-wallet`,
`make chaos-catalog`, `make chaos-slow-pg`.

Переменные окружения каждого скрипта задокументированы в его собственной
шапке (`head -40 deploy/chaos/<скрипт>.sh`) — они не дублируются здесь,
чтобы не разъезжались при правках одного из двух мест.

## Почему процессы на хосте убиваются через `kill -9` по порту, а не `pkill`

`go run` компилирует временный бинарь и исполняет его как дочерний процесс
(имя в `ps` не содержит `cmd/wallet` — только случайный путь во временном
каталоге `go-build*`), поэтому сопоставление по имени команды ненадёжно и
зависит от версии Go. Порт, на котором сервис слушает (`WALLET_GRPC_ADDR`,
`CATALOG_GRPC_ADDR` — из `.env`), не меняется независимо от того, как сервис
был запущен — через `go run`, собранный `bin/wallet` или что угодно ещё,
поэтому `lsof -tiTCP:<порт> -sTCP:LISTEN` — единственный способ, который
одинаково работает во всех этих случаях.

## Почему `slow-pg.sh` не требует `cap_add: NET_ADMIN` в compose

Подробное обоснование — в шапке самого файла (`deploy/chaos/slow-pg.sh`):
коротко, `tc netem` применяется из ОТДЕЛЬНОГО sidecar-контейнера, подключённого
к сетевому namespace цели (`--network container:<target>`), а NET_ADMIN нужен
именно этому sidecar, а не самой базе — значит, `deploy/compose/postgres.yml`
(вне зоны ответственности этой задачи и не должен меняться ради теста)
трогать не пришлось. Это реально проверено на этой машине: `tc qdisc add`
из `nicolaka/netshoot`, подключённого к netns контейнера `pg-catalog`, снял
измеримую задержку на `psql` с хоста и корректно снялся обратно.

Если у используемого docker-демона `--cap-add=NET_ADMIN` запрещён даже для
отдельного контейнера (ограниченная политика, rootless docker) — скрипт сам
обнаруживает эту ситуацию и печатает два запасных варианта без привилегий:
`pg_sleep` в удерживаемой транзакции (конкретный запрос) или
`docker update --cpus` (общая деградация через урезание CPU).

## Что реально проверено на этой машине

- **`tc netem` через сетевой sidecar** — проверено ПО-НАСТОЯЩЕМУ, дважды: на
  одноразовом `alpine`-контейнере и на реальном `pg-catalog` этого проекта
  (`postgres:18-alpine`). Задержка 300мс была видна в замере времени
  подключения с хоста (`psql`) и корректно снималась `tc qdisc del`.
- **Guard-условия всех четырёх скриптов** (нет `docker`, контейнер не
  `running`, никто не слушает порт, нет опубликованной карточки) — прогнаны
  вживую, каждый корректно печатает понятное сообщение и завершается
  ненулевым кодом, а не падает необработанным исключением bash под
  `set -euo pipefail` (был найден и исправлен реальный баг: `pid=$(cmd | cmd2)`
  без `|| true` под `pipefail` роняет скрипт МОЛЧА, если `cmd2` ничего не
  находит — это править дороже в 3 часа ночи, чем сейчас).
- `bash -n` и `shellcheck -S style` — чисто на всех четырёх файлах.

## Что НЕ проверено (честно)

Docker-демон на этой машине сейчас поднят, но реальный стек ИМЕННО из
`deploy/compose/docker-compose.yml` — нет: единственные живые контейнеры
`kafka`/`pg-catalog` в момент проверки принадлежали СТАРОМУ корневому
`docker-compose.yml` (миграция на `deploy/compose/**`, см. `docs/PLAN.md`,
ещё не завершена на этой машине — `git status` показывает оба файла как
`M`/готовящиеся к удалению). Поэтому:

- **`kill-kafka.sh` целиком** (`docker compose stop/start kafka` +
  ожидание readiness catalog) — НЕ прогнан против `deploy/compose`-стека:
  `docker compose -f deploy/compose/docker-compose.yml ps kafka` корректно
  вернул "не running" (правильно — с точки зрения ЭТОГО проекта контейнера
  там нет), но полный сценарий с реальными catalog/media поверх
  `deploy/compose` не выполнялся.
- **`kill-wallet.sh` и `kill-catalog.sh` целиком** (реальная сага, реальный
  circuit breaker, реальные компенсации в Temporal) — НЕ прогнаны: для этого
  нужны поднятые `run-wallet`/`run-catalog`/`run-order`/`run-worker` и
  Temporal, что выходит за рамки задачи (и, по вводным, скорее всего не
  поднимется на этой машине даже если demon работает — не проверялось).
- Само поведение системы под этими сбоями (что outbox действительно
  копится и доезжает, что деньги действительно возвращаются) описано ИЗ
  ЧТЕНИЯ КОДА (`pkg/outbox`, `workflow.go`, `pkg/resilience/breaker.go`) и
  существующих `make demo-kafka-outage`/`make demo-saga-fail`, а не
  подтверждено повторным живым прогоном именно этих новых скриптов.
