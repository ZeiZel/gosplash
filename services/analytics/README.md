# analytics-service

Агрегаты просмотров и покупок поверх ClickHouse. Фаза 4 (`docs/PLAN.md`).

gRPC-контракт: `proto/gosplash/analytics/v1/analytics.proto` (заморожен) —
`TopPhotos(period, limit)` и `PhotoStats(photo_id, period)`. Наружу отдаются
только СВОДКИ — метода «покажи все просмотры фото» здесь нет намеренно,
такой запрос означал бы, что ClickHouse используют как OLTP-хранилище.

Ключевое архитектурное решение фазы (Kafka engine ClickHouse против
консьюмера на Go) разобрано в `docs/adr/0016-clickhouse-kafka-engine.md` —
этот README не повторяет его целиком, только то, что нужно для чтения кода
и схемы.

## Почему для аналитики отдельная база, а не PostgreSQL

У PostgreSQL и ClickHouse противоположные сильные стороны, и дело не в
«ClickHouse быстрее» — дело в том, ДЛЯ ЧЕГО каждый оптимизирован.

**PostgreSQL — строчное хранение (row-oriented).** Данные одной строки
таблицы физически лежат РЯДОМ на диске: чтобы прочитать строку целиком
(например, "фото по id, все поля"), нужен один поход к диску. Обратная
сторона: чтобы посчитать `sum(price_cents)` по миллиону строк, PostgreSQL
всё равно читает КАЖДУЮ строку целиком — `photo_id`, `author_id`,
`viewer_id`, `country`, всё — просто чтобы добраться до одного нужного поля
`price_cents`. Индекс по `ts` подскажет, КАКИЕ строки читать, но не избавит
от чтения ненужных колонок внутри каждой такой строки.

**ClickHouse — колоночное хранение (column-oriented).** Значения ОДНОЙ
колонки всех строк лежат подряд, отдельно от остальных колонок. Запрос
`SELECT sum(views) FROM photo_views_daily WHERE day >= ... GROUP BY photo_id`
читает с диска ТОЛЬКО колонки `day`, `photo_id`, `views` — и не трогает ни
байта из `country`, если бы она там была. На агрегатах по немногим колонкам
из широкой таблицы (а аналитические запросы почти всегда такие) это разница
на порядки, а не на проценты — она видна именно на запросах вида «просуммируй
одну колонку по миллионам строк», и НЕ видна на запросах вида «найди одну
строку по id» (там как раз выигрывает PostgreSQL: см. ниже).

**Правило проекта**: OLTP (заказы, счета, метаданные — единичные строки,
частые точечные изменения) — PostgreSQL. OLAP (просмотры, агрегаты, отчёты —
редко один SELECT читает миллионы строк сразу) — ClickHouse. Смешивать их в
одной базе можно ровно до того момента, когда аналитический отчёт начинает
конкурировать за ресурсы с оформлением заказа (см. `deploy/compose/clickhouse.yml`,
шапка файла — та же мысль).

## Схема: `ORDER BY`, разреженный индекс, отсутствие `UPDATE`

```sql
CREATE TABLE photo_views
(
    photo_id  UUID,
    author_id Int64,
    viewer_id Nullable(Int64),
    ts        DateTime64(3),
    country   LowCardinality(String)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (photo_id, ts)
TTL toDateTime(ts) + INTERVAL 1 YEAR
```

(полный текст — `migrations/auto.go`, с комментариями у каждого решения).

### Почему `ORDER BY (photo_id, ts)`

`ORDER BY` в ClickHouse — это в буквальном смысле порядок хранения строк на
диске внутри каждого парта: ClickHouse физически СОРТИРУЕТ строки по этим
колонкам перед записью. И `PhotoStats` (`WHERE photo_id = ?`), и
материализованное представление `photo_views_daily_mv` (`GROUP BY photo_id`
— см. ниже), фильтруют и группируют ПО ФОТО. Отсортируй таблицу по `(ts,
photo_id)` вместо `(photo_id, ts)` — и `WHERE photo_id = 'x'` превратился бы
в скан всего диапазона времени, потому что строки одного `photo_id`
оказались бы рассеяны по всей таблице, а не лежали бы рядом. `ts` вторым
полем — чтобы внутри одного `photo_id` строки шли по времени, что ускоряет
типичный `WHERE photo_id = ? AND ts >= ?`.

### Что такое "первичный ключ" в ClickHouse — и чем он НЕ является

В PostgreSQL `PRIMARY KEY` — это уникальность плюс B-tree индекс на КАЖДУЮ
строку. В ClickHouse `ORDER BY` (он же по умолчанию и первичный ключ, если
`PRIMARY KEY` не задан отдельно) — это **разреженный индекс по гранулам**:
ClickHouse запоминает значения ключа не для каждой строки, а для каждой
ГРАНУЛЫ (по умолчанию 8192 строк подряд, уже отсортированных по `ORDER BY`).
Найти строку по индексу означает «бинарным поиском по гранулам найти,
в какую гранулу она могла бы попасть, и прочитать эту гранулу целиком (до
8192 строк), а не одну строку».

Прямое следствие: **`ORDER BY`/`PRIMARY KEY` НЕ проверяет уникальность.**
Вставь строку с тем же `(photo_id, ts)` дважды — ClickHouse не откажет и не
заметит: обе строки просто лягут рядом. Это не баг, это то, для чего движок
не предназначен (см. `internal/adapters/clickhouse/integration_test.go
:TestWriter_DublirovaniePriPovtorePosleUpavshegoOffseta` — тест намеренно
демонстрирует именно это поведение, вызванное собственной логикой
консьюмера, см. `ADR 0016`).

### Почему нет `UPDATE` — и что делать вместо него

ClickHouse хранит данные в неизменяемых (immutable) партах: файл, однажды
записанный на диск, не редактируется на месте. `UPDATE`/`DELETE` в
ClickHouse формально существуют (`ALTER TABLE ... UPDATE`), но реализованы
как **асинхронная перезапись всего парта, затронутого условием**, а не как
точечное изменение строки, — операция дорогая и по документации ClickHouse
не предназначена для частого использования (несколько раз в сутки — приемлемо,
на каждый факт бизнес-события — нет).

Вместо `UPDATE`:

- **Append-only.** Изменение факта — это НОВАЯ строка, а не правка старой.
  Например, "исправить страну у уже вставленного просмотра" в этом проекте
  не предусмотрено вовсе — просмотр это факт истории ("посмотрели тогда-то,
  из такой-то страны"), и он не должен становиться неверным задним числом.
- **ReplacingMergeTree — "в конце концов", а не сразу.** Этот движок хранит
  НЕСКОЛЬКО версий строки с одинаковым `ORDER BY` и во время фонового
  MERGE схлопывает их до последней (или по явной колонке версии), оставляя
  одну. Ключевое слово — "во время MERGE": он происходит в БЭКГРАУНДЕ, по
  расписанию, которое ClickHouse выбирает сам, а не по команде приложения.
  Между вставкой дубликата и его схлопыванием — от секунд до часов — обе
  версии строки физически лежат на диске одновременно, и `SELECT` без
  `FINAL` их обе увидит. `FINAL` форсирует схлопывание на лету, но стоит
  заметной доли производительности запроса (весь смысл ReplacingMergeTree —
  переложить дедупликацию на фон, а `FINAL` эту экономию отменяет).
  Поэтому таблицы этого сервиса — обычный `MergeTree`, а не
  `ReplacingMergeTree`: дубликаты, которые здесь вообще могут появиться
  (см. ADR 0016, "batch-before-commit"), — редкое следствие падения
  процесса, а не нормальный сценарий работы, и добавлять `ReplacingMergeTree`
  "на всякий случай" значило бы платить его цену (асинхронность, `FINAL`
  для честного `SELECT`) там, где реальной потребности пока нет. Взять его
  стоит, когда дубликаты СТАНУТ обычным делом — например, если
  консьюмер начнёт двигаться к строгому at-least-once с более частыми
  перезапусками, — а не заранее.

## `LowCardinality(String)` — когда лучше, а когда хуже обычного `String`

`LowCardinality(T)` — это словарное кодирование: ClickHouse строит маленький
словарь уникальных значений колонки (`{0: "RU", 1: "US", 2: "DE", ...}`) и
хранит в самой колонке не строки, а индексы в этот словарь (обычно 1 байт на
значение). Выигрыш двойной: место на диске (словарь на всю таблицу —
килобайты, а не байты строки на каждую из миллионов строк) и скорость
сравнения (`GROUP BY country`, `WHERE country = 'RU'` сравнивают маленькие
целые числа, а не строки посимвольно).

Используется для `country`: кодов стран в мире меньше 300, то есть
кардинальность (число уникальных значений) заведомо низкая независимо от
объёма таблицы.

**Когда `LowCardinality` ХУЖЕ обычного `String`**: при ВЫСОКОЙ кардинальности
— email, URL, свободный текст, вообще любая колонка, где уникальных значений
сравнимо с числом строк. Тогда словарь разрастается почти до размера самих
данных (никакой экономии места), а на каждую вставку новых уникальных
значений ClickHouse тратит время на дозапись словаря — то есть платится
цена перестройки структуры без единого байта выигрыша взамен. Именно поэтому
`photo_id`/`viewer_id` в этом сервисе — обычные `UUID`/`Int64`, а не
`LowCardinality`: у них кардинальность близка к числу строк по определению.

## `photo_views_daily` — материализованное представление

```sql
CREATE TABLE photo_views_daily
(
    day      Date,
    photo_id UUID,
    views    UInt64
)
ENGINE = SummingMergeTree(views)
ORDER BY (photo_id, day);

CREATE MATERIALIZED VIEW photo_views_daily_mv
TO photo_views_daily
AS SELECT toDate(ts) AS day, photo_id, count() AS views
FROM photo_views GROUP BY day, photo_id;
```

`TopPhotos` не может позволить себе `sum()`/`count()` по всей таблице
`photo_views` на каждый запрос — это ровно тот сценарий "чужой аналитический
запрос мешает horячему пути", от которого предостерегает
`deploy/compose/clickhouse.yml`. Представление срабатывает на каждый `INSERT`
в `photo_views` и сразу пишет предпосчитанную сумму в `photo_views_daily` —
`TopPhotos` читает уже маленькую (по сравнению с сырыми просмотрами) таблицу.

`SummingMergeTree(views)` складывает строки с одинаковым `ORDER BY`
**во время фонового мержа**, а не сразу — то же самое "в конце концов", что
и `ReplacingMergeTree` выше. Из этого следует, что на диске в любой момент
может лежать НЕСКОЛЬКО ещё не слитых строк на одну и ту же пару
`(photo_id, day)`. Поэтому `internal/adapters/clickhouse/repository.go`
всегда пишет явный `sum(views)` в запросах к `photo_views_daily`, а не
полагается на то, что строка на `(photo_id, day)` уже единственна, — это
не перестраховка, а прямое следствие того, как устроен движок.

## `unique_viewers_approx` — почему в ClickHouse, а не в Redis HLL

В проекте уже есть готовый HyperLogLog в Redis (`pkg/redisx/hll.go`,
`PFADD`/`PFCOUNT`) — тот же математический приём (приблизительный
`COUNT(DISTINCT)` в константной памяти), которым решено НЕ пользоваться
здесь. Вместо него — `uniqCombined(viewer_id)` прямо в ClickHouse.

Redis HLL был бы уместен, если бы ответ был нужен МГНОВЕННО и БЕЗ похода в
аналитическую базу вообще — как `catalog`'овский `ViewCounter`
(`internal/adapters/redis` каталога) считает счётчик просмотров для ленты:
там каждый лишний поход в другую систему на КАЖДЫЙ показ карточки был бы
заметен. `PhotoStats` устроен иначе: он и так один аналитический запрос в
ClickHouse (за `views`, `purchases`, `revenue_cents`), и добавить туда же
одно число `uniqCombined` не стоит НИЧЕГО сверх уже сделанного похода в
базу. А вот завести Redis HLL стоило бы РЕАЛЬНО: пришлось бы вызывать
`PFADD` на каждый просмотр из ВТОРОГО места (либо из catalog — сервиса вне
зоны ответственности этой фазы, либо из `internal/adapters/kafka` этого
сервиса) — то есть завести ВТОРОЙ источник правды, который неизбежно
разойдётся с ClickHouse при любой потере сообщения одним из двух
независимых потребителей одного и того же топика. Один источник правды
дороже стоит здесь, чем миллисекунды задержки, которые Redis мог бы
сэкономить, — задержки, которая и так уже не на горячем пути.

`uniqCombined`, а не `uniqExact`: `uniqExact` держит в памяти множество ВСЕХ
увиденных `viewer_id` ради точного ответа — на миллиардах строк это гигабайты
оперативной памяти сервера ради точности, которая никому не нужна (см.
комментарий к `unique_viewers_approx` в `analytics.proto`: погрешность в
доли процента не меняет ни одного решения). `uniqCombined` — гибрид: на
малом множестве считает точно, на большом сам переключается на HyperLogLog
с постоянной памятью — то есть не платит погрешность там, где в ней нет
нужды.

## GORM для ClickHouse не используется

Хотя `gorm.io/driver/clickhouse` существует и присутствует среди
транзитивных зависимостей монорепы, этот сервис ходит в ClickHouse обычным
SQL через `clickhouse-go/v2` напрямую (`internal/adapters/clickhouse`,
`migrations/auto.go`). Причины подробно расписаны в шапке
`migrations/auto.go`, коротко:

1. `AutoMigrate` не умеет `ENGINE = MergeTree`, `PARTITION BY`, `ORDER BY`,
   `TTL` — это не свойства колонки или индекса в терминах GORM, а сама суть
   движка ClickHouse.
2. GORM рассчитан на ЭВОЛЮЦИЮ схемы (добавить колонку к существующей
   таблице). В ClickHouse смена `ORDER BY`/`PARTITION BY`/движка задним
   числом — это пересоздание таблицы, а не `ALTER`: решение о структуре
   хранения принимается один раз при создании.
3. Материализованное представление — не таблица в понимании GORM, а
   сохранённый `SELECT`, который движок сам перевыполняет на каждую вставку;
   аналога этому в GORM нет.

## Почему консьюмер батчит вставки, а не пишет по одной строке

Каждый `INSERT` в ClickHouse — это новый ПАРТ на диске (immutable-файл),
независимо от того, одна в нём строка или миллион. Построчная вставка на
потоке просмотров (их на порядки больше остальных событий проекта — см.
комментарий к `PhotoViewed` в `events.proto`) означала бы тысячи мелких
партов в секунду, а фоновый merge не успевал бы их сливать в более крупные
— именно так рождается предупреждение ClickHouse `"Too many parts"` и
деградация вставки. Поэтому:

- Kafka-консьюмер (`internal/adapters/kafka` → `internal/adapters/clickhouse/
  batch.go`) копит строки и вставляет их пачками, `Add()` блокирует
  вызывающего до завершения вставки его пачки (подробности и цена — ADR 0016).
- `cmd/seed` (демо-утилита, `mk/analytics.mk: analytics-seed`) вставляет
  сразу батчами по `-batch` строк (по умолчанию 50 000) — 5 миллионов строк
  по одной заняли бы часы и создали бы миллионы партов; батчами — секунды и
  десятки партов.

## Тот же запрос — в PostgreSQL

`SELECT photo_id, count(*) FROM photo_views WHERE ts >= now() - interval '7
days' GROUP BY photo_id ORDER BY count(*) DESC LIMIT 100` на миллионах строк
в PostgreSQL с обычным `btree`-индексом по `ts`:

- индекс находит строки за неделю быстро, но дальше PostgreSQL читает КАЖДУЮ
  такую строку целиком (все её колонки, не только `photo_id`) — то, что
  ClickHouse вообще не делает (см. "почему отдельная база" выше);
- `GROUP BY` и сортировка результата — CPU-работа, сравнимая в обеих базах,
  но она применяется уже К БОЛЬШЕМУ объёму прочитанных данных в PostgreSQL;
- при полном объёме таблицы (`analytics-seed`, 5 млн строк и больше) разница
  становится видна на порядок, а не на проценты — это и демонстрирует
  `make demo-clickhouse`, которая честно гоняет ОДИН И ТОТ ЖЕ по смыслу
  запрос в обеих базах на сопоставимом объёме и печатает оба числа (см.
  `mk/analytics.mk`, раздел "честное ограничение этой демонстрации" —
  сравнение иллюстративное, не строгий бенчмарк).

## Конфигурация

Секции `Analytics` в `pkg/config` нет и в этой фазе не заводится — это
осознанное отступление от правила docs/STYLE.md «`os.Getenv` только в
`pkg/config`», подробно объяснённое в `internal/config/config.go` (шапка
пакета). Кратко: `pkg/config` вне зоны ответственности фазы 4, а
`CLICKHOUSE_*`/`ANALYTICS_*` уже объявлены в `.env`/`.env.example`. Перенос
`internal/config` в `pkg/config.AnalyticsConfig` — работа интегратора.

Переменные, которые сервис читает локально (`internal/config`):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `CLICKHOUSE_ADDR` | native-адрес ClickHouse | `localhost:59440` |
| `CLICKHOUSE_DB` | база | `gosplash` |
| `CLICKHOUSE_USER` / `CLICKHOUSE_PASSWORD` | креды | `gosplash` / `gosplash` |
| `ANALYTICS_GRPC_ADDR` | адрес gRPC-сервера | `:9106` |
| `ANALYTICS_HTTP_ADDR` | `/healthz`, `/readyz` | `:8106` |
| `ANALYTICS_METRICS_ADDR` | `/metrics`, `/debug/pprof` | `:8206` |
| `KAFKA_CONSUMER_GROUP_ANALYTICS` | префикс consumer group | `analytics` |
| `ANALYTICS_CH_BATCH_SIZE` / `ANALYTICS_CH_FLUSH_INTERVAL` | батчинг просмотров | `5000` / `2s` |
| `ANALYTICS_CH_PURCHASE_BATCH_SIZE` / `ANALYTICS_CH_PURCHASE_FLUSH_INTERVAL` | батчинг покупок (меньше — их на порядки реже) | `100` / `1s` |

Общее (`Kafka.Brokers`, `Observe`, `GRPC.DefaultTimeout`) — из
`config.Load()` (`pkg/config`), как у всех сервисов монорепы.

## Что требует Docker

- `go build ./...`, `go vet ./...`, `go test ./... -count=1`, `gofmt -l .` —
  **не требуют** Docker: `internal/app` тестируется поддельными портами,
  `internal/adapters/clickhouse/batch_test.go` и `repository_test.go`
  проверяют чистую логику (батчинг, построение SQL) без сети,
  `internal/adapters/kafka` тестируется без реального брокера (конверт
  собирается и разбирается в памяти).
- `go test -tags=integration ./...` — **требует** Docker: поднимает
  одноразовый контейнер `clickhouse/clickhouse-server:25.8`
  (testcontainers-go) на каждый тест, накатывает миграции и проверяет
  вставку+чтение сквозь настоящий движок, включая материализованное
  представление и намеренную демонстрацию дублирования строки при повторной
  доставке (см. ADR 0016).
