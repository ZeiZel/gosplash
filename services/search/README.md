# search — полнотекстовый поиск по каталогу

Фаза 5. Отдельный сервис (не метод catalog), потому что у поиска другой
индекс, другая модель отказа (Elasticsearch может лежать, пока каталог
работает) и другой жизненный цикл (индекс перестраивается целиком через
alias, база каталога — нет). Контракт — `proto/gosplash/search/v1/search.proto`.

Этот README начинается с PostgreSQL не для вида: прежде чем заводить второе
хранилище, нужно честно понять, чего не хватает первому. Дальше — что оно
даёт и что стоит.

## Сначала — как это делается в PostgreSQL

В PostgreSQL уже есть полнотекстовый поиск: `tsvector` + `GIN`-индекс.
Для карточки каталога (`title`, `tags`, `author_name`) это выглядело бы так:

```sql
ALTER TABLE listings ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('russian', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('russian', coalesce(author_name, '')), 'B') ||
    setweight(to_tsvector('simple', array_to_string(tags, ' ')), 'C')
  ) STORED;

CREATE INDEX listings_search_idx ON listings USING GIN (search_vector);

-- Поиск с ранжированием:
SELECT id, title, ts_rank(search_vector, query) AS rank
FROM listings, plainto_tsquery('russian', 'закат на море') AS query
WHERE search_vector @@ query
  AND status = 'published'
ORDER BY rank DESC
LIMIT 20;

-- Фильтр по тегам и цене — обычный WHERE, ничего специального:
SELECT id, title
FROM listings
WHERE search_vector @@ plainto_tsquery('russian', 'закат')
  AND tags && ARRAY['море']
  AND price_cents BETWEEN 100 AND 5000;
```

Это реально работает, не требует нового сервиса и живёт в той же
транзакции, что и остальные данные каталога. Для многих проектов этого
достаточно НАВСЕГДА, и заводить Elasticsearch им не нужно.

## Чего в этом решении не хватает — честно

- **Ранжирование.** `ts_rank`/`ts_rank_cd` — это не BM25. Он взвешивает
  совпадения по весам (`setweight` выше: A/B/C), но не учитывает длину
  документа (BM25 намеренно штрафует совпадение в длинном документе меньше,
  чем в коротком — "закат" в заголовке из двух слов значит больше, чем
  "закат" в заголовке из двадцати) и не умеет несколько независимо
  настраиваемых полей с разной значимостью без ручного жонглирования весами
  A/B/C/D (их всего четыре, и они глобальны для базы, а не для запроса).
  Написать BM25 поверх `tsvector` руками — это не полдня работы, это
  отдельный движок ранжирования внутри приложения.
- **Фасеты.** "Сколько карточек под каждым тегом в ТЕКУЩЕЙ выдаче" — в SQL
  это `GROUP BY tag` ПОСЛЕ разворачивания `tags` через `unnest`, отдельным
  запросом на каждый фасетируемый фильтр (в поиске фасет по тегам обычно
  считается по тому же query+остальным фильтрам, но БЕЗ фильтра по самим
  тегам — иначе после выбора одного тега исчезают остальные варианты). Три
  фасета — три дополнительных запроса на каждый поиск, и они сканируют то
  же множество строк, что и основной запрос, только agregируют иначе.
  Elasticsearch считает все фасеты ОДНИМ запросом (`aggs`), потому что
  агрегация в нём — это побочный проход по тем же посчитанным множествам
  документов, а не отдельный SQL-запрос.
- **Опечатки.** `pg_trgm` умеет находить похожие строки по триграммам
  (`similarity()`, `%`-оператор) — но это ДРУГОЙ индекс и ДРУГОЙ оператор,
  чем `tsvector @@ tsquery`, и они плохо сочетаются в одном запросе:
  либо полнотекстовый поиск по стеммированным токенам (быстрый, но нулевая
  устойчивость к опечаткам), либо триграммное сходство по сырой строке
  (терпит опечатки, но не понимает морфологию и не масштабируется на
  многословные запросы так же дёшево). Комбинировать оба — значит вручную
  склеивать результаты двух разных механизмов и решать, чей ранг важнее.
- **Масштабирование.** GIN-индекс живёт в той же базе, что и OLTP-нагрузка
  каталога (вставки/обновления карточек). Тяжёлый поисковый трафик и
  обновления строк конкурируют за один и тот же буферный кэш и один и тот
  же WAL. У Elasticsearch кластер шардируется и масштабируется отдельно от
  источника данных — ценой того, что источник данных теперь два (см. ниже).

## Почему всё-таки Elasticsearch — без религии

Elasticsearch закрывает все четыре пункта выше "из коробки": BM25 по
умолчанию, `aggs` для фасетов одним запросом, `fuzziness` для опечаток,
свой шардируемый кластер отдельно от OLTP. Подробный разбор решения и его
цены — `docs/adr/0017-elasticsearch-protiv-tsvector.md`. Коротко цена:

- **Ещё одно хранилище.** Отдельный кластер, отдельный мониторинг, отдельные
  бэкапы, отдельная кривая обучения (query DSL — не SQL).
- **Ещё одна копия данных.** Всё, что лежит в индексе, уже лежит в catalog.
  Это дублирование намеренное (иначе не было бы кэша поиска отдельно от
  системы записи), но это реальные лишние байты и реальная возможность
  разъехаться.
- **Eventual consistency.** Индекс наполняется асинхронно из Kafka
  (`catalog.listing.published`). Между "карточка опубликована в catalog" и
  "карточка находится в поиске" проходит время — обычно доли секунды, но
  не ноль. Для витрины фотостока это приемлемо, для, скажем, отображения
  "ваш только что созданный заказ" — уже нет (и там поиск не используется).
- **JVM.** Elasticsearch — это Java-процесс с собственной кучей, собственным
  GC и собственными паузами. Это ещё одна система, у которой "тормозит"
  может означать "идёт full GC", а не "медленный диск" или "долгий SQL".

## Индекс

Маппинг — `internal/adapters/es/mapping.go`, `dynamic: strict`, применяется
при старте, если индекс ещё не существует (`internal/adapters/es/client.go`,
`Client.EnsureIndex`). Поля: `title` (мультиполе `russian`/`english`),
`tags` (`keyword`), `author_name` (`text` + `.keyword`), `price_cents`
(`integer`), `author_id` (`long`), `status`/`currency` (`keyword`),
`published_at` (`date`). Разбор каждого решения — комментарии в самом файле
маппинга; там же — почему `dynamic: strict`, а не «пусть Elasticsearch сам
разберётся».

Индекс никогда не создаётся и не меняется вручную — только через
`EnsureIndex` (первый запуск) и `tools/search-reindex` (смена схемы).
Сервис всегда обращается по имени **alias** (`SEARCH_INDEX_ALIAS`, по
умолчанию `listings`), никогда по физическому имени индекса.

## Консьюмер: идемпотентность через версионирование

Слушает `catalog.listing.published` (`internal/app/indexer.go`). Вместо
таблицы `processed_events` (как в catalog) — версия документа:
`version = occurred_at конверта в мс`, `version_type: external_gte`.
Elasticsearch сам отбрасывает более старую по версии запись. Почему здесь
этого достаточно, а таблица не нужна — потому что «применить событие» в ES
это ОДНА операция на ОДИН документ, а не несколько связанных, которые
нужно закоммитить/откатить атомарно (ради чего и заводится
`processed_events` в catalog). Подробности и разбор `version_conflict` как
штатного, а не ошибочного исхода — комментарии в `internal/app/indexer.go`
и `internal/adapters/es/bulk_indexer.go`.

Запись идёт пачками через `_bulk` (`internal/adapters/es/bulk_indexer.go`),
с синхронным ожиданием результата — offset коммитится в Kafka только после
того, как документ реально долетел до Elasticsearch, а не в момент, когда
он лёг в буфер. Разбор компромисса (добавленная задержка при низком
трафике, настоящий bulk при высоком) — в комментарии пакета там же.

## Поиск

`multi_match` по `title`/`author_name` с `fuzziness: AUTO`; `tags`/`price`/
`author_id` — в `filter`-контексте (не влияют на `_score`, кэшируются);
фасеты по тегам — `aggs` тем же запросом; пагинация — `search_after` с
tie-breaker по `listing_id` (не `_id` — см. комментарий в
`internal/adapters/es/query_builder.go`, у служебного `_id` fielddata
отключена по умолчанию). Все решения разобраны в комментариях
`internal/adapters/es/query_builder.go` и `internal/adapters/es/cursor.go`.

## Конфигурация

`pkg/config` не тронут (задание фазы: секции `search` там сознательно нет —
это интеграционная работа за пределами этой фазы). Локальный,
явно помеченный как временный пакет `internal/config` читает:

| Переменная                     | Смысл                                   |
| ------------------------------- | ---------------------------------------- |
| `ELASTICSEARCH_ADDRS`           | адреса узлов кластера, через запятую     |
| `SEARCH_INDEX_ALIAS`            | имя alias'а (по умолчанию `listings`)    |
| `SEARCH_GRPC_ADDR`              | адрес gRPC-сервера                       |
| `SEARCH_HTTP_ADDR`              | адрес служебного HTTP (`/healthz`, `/readyz`) |
| `SEARCH_METRICS_ADDR`           | адрес `/metrics` и `/debug/pprof`        |
| `KAFKA_CONSUMER_GROUP_SEARCH`   | consumer group для `catalog.listing.published` |

Остальное (Kafka-брокеры, наблюдаемость, gRPC-таймауты) берётся из
`pkg/config.Load()`, как и у всех сервисов проекта.

## Запуск

Нужен Docker (`deploy/compose/elasticsearch.yml`, `deploy/compose/kafka.yml`,
поднимаются общим `docker compose` из корня — см. главный `Makefile`).
Локально Elasticsearch слушает `http://localhost:59200`, security выключена.

```
make up            # поднять инфраструктуру, включая elasticsearch
make run-search     # если цель заведена в главном Makefile интегратором
# или напрямую:
cd services/search && go run ./cmd/search
```

Цели для ручной проверки — `mk/search.mk` (`make help` покажет короткое
описание каждой).

## Тесты

`go test ./...` — без Docker: построение тела ES-запроса, разбор ответа,
курсор, классификация ошибок, консьюмер и gRPC-сервер против подделок
портов. `go test -tags=integration ./...` — против настоящего
Elasticsearch в testcontainers-go: индексация, поиск с опечаткой, фасеты,
пагинация, версионирование. `tools/search-reindex` тестирует переключение
alias тем же способом, отдельно от этого сервиса.
